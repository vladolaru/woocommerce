# H18 Express Checkout Analysis

> **Prompt:** "Continue working toward the active thread goal."

## Starting Point

H17 closed as harness hardening only. The remaining baseline blockers include non-WooPay express checkout parity for Apple Pay, Google Pay, and Amazon Pay; this is both an A3 merchant/shopper-facing checkout gap and an N7c bundle failure because the target bundle comparison still reports missing non-WooPay express checkout JS/CSS. This H18 analysis scopes the next larger slice around that gap, while keeping WooPay/card work as sibling surfaces rather than parents of express checkout.

## Source-Backed Requirements

- `design-spec.md` states checkout flows must preserve classic, Blocks, express, and WooPay behavior, including express checkout buttons and the `wcpay_payment_fields_js_config` contract.
- `bc-manifest.md` classifies express checkout in Bucket A and requires hard-preserve behavior for surviving shopper-facing surfaces and Tracks events.
- `spec-conformance-baseline.md` records non-WooPay express checkout as blocker 1: native Core currently exposes WooPay express config, while the reference WooPayments client has distinct Express Checkout Element paths for Apple Pay / Google Pay (`payment_request`) and Amazon Pay (`amazon_pay`).
- `staging-log.md` records H16 Tracks continuity as explicitly excluding non-WooPay express checkout events until native Apple Pay / Google Pay / Amazon Pay exists.

## Reference Map

- Bootstrap: the standalone WooPayments client creates `WC_Payments_WooPay_Button_Handler`, `WC_Payments_Express_Checkout_Ajax_Handler`, `WC_Payments_Express_Checkout_Button_Handler`, and `WC_Payments_Express_Checkout_Button_Display_Handler` together from `WC_Payments::maybe_display_express_checkout_buttons()`.
- Classic render hooks: `class-wc-payments-express-checkout-button-display-handler.php` hooks product, cart, checkout, and pay-for-order surfaces and renders a shared `wcpay-express-checkout-wrapper` containing the WooPay placeholder, the ECE placeholder, order-attribution inputs, and a separator.
- PHP ECE config/enqueue: `class-wc-payments-express-checkout-button-handler.php` builds `wcpayExpressCheckoutParams`, enqueues `dist/express-checkout` plus `dist/express-checkout.css`, and attaches the same data to classic ECE and Blocks checkout.
- Eligibility/settings helper: `class-wc-payments-express-checkout-button-helper.php` reads `express_checkout_{product|cart|checkout}_methods`, maps Apple/Google to `payment_request`, and gates Amazon Pay through feature/account/tax constraints.
- Store API normalization: `class-wc-payments-express-checkout-ajax-handler.php` normalizes Apple/Google/Amazon address quirks for Store API requests carrying the tokenized-cart headers.
- Product-page isolation: `class-wc-payments-payment-request-session.php` and `class-wc-payments-payment-request-session-handler.php` support tokenized product-page Store API carts so express checkout can price and check out a product without polluting the shopper's normal cart.
- Asset split: WooPayments builds `express-checkout`, `blocks-checkout`, `checkout`, `woopay`, `woopay-express-button`, and `woopay-direct-checkout` as distinct assets.
- Blocks ECE: `client/express-checkout/block-buttons/index.js` registers Apple Pay, Google Pay, and Amazon Pay as separate Blocks express payment methods, all backed by `woocommerce_payments_express_checkout` and per-method Stripe ECE overrides.
- Classic ECE: `client/express-checkout/shortcode-buttons-express/index.js` mounts Stripe `expressCheckout`, refreshes on cart/checkout updates, handles click/ready/cancel/confirm/shipping events, and routes order placement through Store API.
- Tracks: `client/express-checkout/tracking.js` emits Apple Pay and Google Pay load/click shopper events; the display handler marks `wcpay_applepay*` and `wcpay_gpay*` as all-store events through `wcpay_tracks_event_properties`.

## Native Gap Map

- Blocks native Core has no payment-request/ECE handle. `WooPayments.php` only registers card and conditional WooPay handles; `webpack-entries.js` only has `wc-payment-method-woopayments` and `wc-payment-method-woopayments-woopay`.
- The native card Blocks entry intentionally stays card-only and disables Stripe Payment Element wallets. That is correct for card parity and should not become the non-WooPay express owner.
- The native WooPay Blocks entry is the only `registerExpressPaymentMethod()` call and registers only `woopay`.
- Classic native Core registers only `wc-woopayments-checkout` and `wc-woopayments-woopay`; there is no classic payment-request/ECE script or CSS handle.
- `WooPaymentsWooPaySessionController` registers the express render hooks but is WooPay-gated and only renders `#wcpay-woopay-button`; using it directly for Apple/Google would incorrectly make payment request depend on WooPay eligibility.
- `WooPaymentsWooPaySessionService` exposes some legacy-shaped express data and nonces, but `enabled_methods` is `array( 'woopay' )` only. This confirms there is no renderable native `payment_request` surface.
- Backend residue exists for wallet-originated display details: `WooPaymentsCheckoutAjaxController` and `WooPaymentsProviderGatewayAdapter` can title Apple Pay / Google Pay charges, and account/setup sync knows about wallet capabilities. That is not a frontend flow.

## Architecture Decision

H18 should add a provider-level express checkout owner parallel to both card and WooPay. The new owner should be a native WooPayments provider adapter/controller pair, gated by native runtime ownership and WooPayments account/card readiness, not by WooPay/platform-checkout eligibility. Card remains card-only. WooPay remains WooPay-specific. The common abstraction is "provider-level express checkout method supplied by WooPayments", not "WooPay button".

The high-throughput implementation target for this slice is Apple Pay / Google Pay payment-request parity first: PHP config/hooks, separate Blocks express asset, separate classic asset/CSS, Store API checkout data, address/tokenized-cart normalization where needed, and Tracks load/click continuity. Amazon Pay remains a source-backed parity blocker unless a native backend processing contract is verified and implemented; exposing an Amazon button without that contract would hide risk rather than close it.

## Measurement Note

Bundle and performance gates for H18 should be used honestly. Bundle ownership and conditional loading are deterministic: the new payment-request assets must be separate from card and WooPay and only returned/enqueued when eligible. Runtime performance numbers around browser checkout are likely variable in local wp-env; use them as smoke signals for large deltas that suggest something is wrong, not as exact proof. If a measurement is noisy or incomplete, record it as such instead of upgrading it to a pass.

## Review Findings

- 2026-06-17 22:05: Performance review (`Bohr the 2nd`) requested changes for two asset-loading leaks: the Blocks express checkout script handle can be returned to Mini-Cart dependency collection and preloaded on non-cart/non-checkout pages, and the classic ECE controller treats cart/checkout block pages as classic-supported surfaces, causing duplicate classic/Blocks express checkout loading. The CSS side of the classic/Blocks leak was independently reproduced in the browser: classic shortcode checkout initially loaded Blocks WooPayments payment-method CSS, then after the first style gate fix the Blocks checkout still loaded classic WooPayments styles. Current fix direction is fail-closed surface ownership: Blocks assets only for block cart/checkout surfaces, and classic assets only for classic cart/checkout surfaces until product/pay-for-order support is explicitly implemented.
- 2026-06-17 22:05: Architecture review (`Nash the 2nd`) requested changes for five issues: Blocks WooPayments integration is not gated by `NativePaymentsRuntimeArbiter`, product and pay-for-order classic hooks are broader than the current Store API cart checkout client supports, classic ECE depends on `stripe` without registering Stripe.js itself, classic ECE still enqueues on block cart/checkout pages, and missing per-context express settings are treated as explicit empty arrays so legacy-only `payment_request=yes` stores can miss fallback behavior. Fix direction is to inject the arbiter into Blocks WooPayments and gate `is_active()`, restrict H18 classic hooks to cart/checkout while leaving product/pay-for-order as tracked follow-up parity, register Stripe.js in the ECE controller before enqueue, add a shared block-surface guard for classic ECE and WooPay, and update `WooPaymentsExpressCheckoutService` to distinguish absent per-context settings from explicit empty lists.
- 2026-06-17 22:05: Reference-integrity review (`Ramanujan the 2nd`) requested changes for Stripe ECE option shapes and reference contracts: Blocks and classic ECE pass `buttonTheme` and `buttonType` as scalar strings instead of per-wallet objects, both omit `klarna: 'never'` in `paymentMethods`, pay-for-order would emit the wrong context if kept in this slice, and Tracks all-store metadata is written at the top level instead of under `record_event_data.track_on_all_stores`. Fix direction is to emit per-wallet Apple Pay / Google Pay button option maps, explicitly disable Link/PayPal/Amazon Pay/Klarna in this native payment-request slice, remove pay-for-order from H18 hooks rather than emitting an unsupported context, and update the Tracks filter payload plus tests.
