# H19 Remaining Express Checkout Analysis

> **Prompt:** "Make sure you don't over-index on what is reliably measurable. Best to be honest about the possibilities and not chase unreliable numbers. Or at least use them honestly as stop gaps for big deltas in performance to inform that we may be doing something wrong, if their variability is high. But give it a good shot first."

## Starting Point

H18 closed native Apple Pay and Google Pay express checkout parity for cart and checkout, with separate Core-owned Blocks/classic bundles and an honest performance disposition: deterministic asset/bundle boundaries are hard gates, while local browser timing remains advisory smoke unless repeatable. The remaining express checkout parity gap is larger than a single button toggle: Amazon Pay, product-page payment-request checkout, and pay-for-order payment-request checkout each carry backend/context contracts that need source verification before native Core can expose them without hiding regressions.

## Working Scope

This slice should keep card, WooPay, and non-WooPay express checkout at the same provider-owned abstraction level. It should not tie card rendering to WooPay, and it should not expose Amazon/product/pay-for-order surfaces until native request construction, order/session context, styling/assets, Tracks, and backend processing contracts are source-backed. The likely high-throughput chunk is "remaining express checkout surfaces" rather than three tiny slices, but the implementation must still fail closed for any sub-surface whose contract cannot be verified locally.

## Measurement Position

For H19, use deterministic evidence as pass/fail where possible: source parity maps, emitted config shape, asset ownership/conditional loading, unit/Jest assertions, browser DOM/asset checks, and harness money-path reconciliation when a real local flow can be driven. Treat local interaction timing as a stop-gap signal for large regressions only. If Stripe wallet availability, browser domain restrictions, or local Transact state make a runtime signal non-deterministic, record that limitation instead of upgrading it to a pass.

2026-06-17 22:57 update: The performance gate should not chase unreliable precision. A repeated, controlled browser measurement can inform whether a change created a large regression, but noisy local timing stays advisory unless the variance is low enough to make the delta meaningful. Deterministic bundle membership, conditional loading, request-contract shape, and source-backed behavior remain the stronger pass/fail gates for this slice.

## Local Source Findings

- 2026-06-17 22:55: Reference Amazon Pay is not a pure frontend switch. `WC_Payments_Express_Checkout_Button_Helper::can_use_amazon_pay()` disables standalone Amazon Pay when express checkout is shown in payment methods, requires the Amazon feature flag, looks up the split Amazon Pay gateway, requires `is_available_for_express_checkout()`, and blocks billing-address-based tax except on pay-for-order. It then adds `amazon_pay` to `enabled_methods` only when the current product/cart/checkout location setting includes it.
- 2026-06-17 22:55: Reference Express Checkout Elements send Stripe payment method types for enabled express methods. The classic `shortcode-buttons-express` path builds `paymentMethodTypes` from `enabled_methods`: `payment_request` maps to `card`, and `amazon_pay` maps to `amazon_pay`. The reference gateway validates submitted `wcpay-express-payment-method-types` against a server-authoritative allow-list from `get_allowed_express_payment_method_types()` before putting it on the intent request.
- 2026-06-17 22:55: Native H18 frontend and backend are card-wallet only. The Blocks and classic native ECE assets explicitly pass `amazonPay: 'never'` and use `paymentMethodTypes: ['card']`. `WooPaymentsProviderGatewayAdapter::build_native_charge_request_data()` and `build_native_setup_intent_request_data()` also hardcode `payment_method_types => ['card']`. Therefore Amazon Pay must not be exposed until native Core has a provider-owned express payment-method-types request path with server validation and tests.
- 2026-06-17 22:55: Reference product-page payment request is a separate cart/session contract. `WC_Payments_Payment_Request_Session` swaps the Store API session handler only when the `X-WooPayments-Tokenized-Cart-Session-Nonce` header verifies, issues `X-WooPayments-Tokenized-Cart-Session`, supports ephemeral-cart cleanup, and protects the shopper's real cart on the order-received redirect. Reference JS uses `ExpressCheckoutCartApi.useSeparateCart()` plus `addProductToCart()` on product-page click, and only sends the session nonce on product pages.
- 2026-06-17 22:55: Native H18 intentionally has only the shell of that product-page contract. It emits `tokenized_cart_session_nonce` and its frontend helper has an `includeSessionNonce` branch, but the controller never registers product-page hooks, the service normalizes unknown contexts back to checkout, `product` config is an empty array, there is no native payment-request session handler, and the native frontend does not add product data to an isolated Store API cart. Product-page ECE should remain fail-closed until that full session/product compatibility contract is ported.
- 2026-06-17 22:55: Reference pay-for-order uses Store API order endpoints rather than cart checkout. The display handler adds order id/key/billing email to `wcpay_payment_fields_js_config` on supported order-pay pages, and JS switches to `ExpressCheckoutOrderApi`, which calls `/wc/store/v1/order/{id}` then `/wc/store/v1/checkout/{id}` with key and billing email while preserving the order's billing/shipping address. Native H18 does not expose order-pay ECE; its service does not preserve a `pay_for_order` context, and its classic frontend always posts `/wc/store/v1/checkout`. Pay-for-order should remain fail-closed until native order-pay config and Store API order checkout handling are implemented and compared against reference.

## Sidecar Reconciliation

- 2026-06-17 23:03: Parfit's local WPCOM/Transact read-only pass confirms the active processing contract is WCPay V1 `POST /wcpay/intentions`, not Transact V2. The endpoint accepts `confirmation_token`, `payment_method`, `payment_method_types`, `payment_method_options`, metadata, capture method, return URL, and related PaymentIntent fields. Native must keep using the V1-shaped request until a V2 contract is explicitly available for these methods.
- 2026-06-17 23:03: Platform `confirmation_token` handling is explicitly compatible with ECE. When a confirmation token is present, WPCOM clears direct `payment_method` and `mandate_data` before proxying to Stripe, fetches the confirmation token, and uses `payment_method_preview` for fee calculation. Native should continue sending either a confirmation token or a payment method, not both, and should not attach mandate data to confirmation-token requests.
- 2026-06-17 23:03: Platform Amazon Pay handling is method-agnostic at request time: the signal is `payment_method_types[] = amazon_pay` or a confirmation-token preview whose type is `amazon_pay`. Amazon becomes special downstream for fee/refund behavior, where WPCOM reads nested `amazon_pay.funding.card` details and may refund application fees for non-card Amazon funding. Native Core needs to preserve the method type accurately, but it does not need a separate request transport for Amazon Pay on the V1 path.
- 2026-06-17 23:03: Lovelace's reference map confirms Amazon Pay requires both feature/account gates and backend validation. Reference WooPayments only enables Amazon when the Amazon feature is enabled, account data does not disable ECE confirmation tokens, the split Amazon gateway is available for express checkout, the current surface setting includes `amazon_pay`, and billing-address tax restrictions allow it. The Store API payment payload includes `wcpay-express-payment-method-types`, and the server validates it against an allowed list before putting it on the intent request.
- 2026-06-17 23:03: Banach's native map confirms H18 disables Amazon in both classic and Blocks ECE, registers only Apple Pay and Google Pay as Blocks express methods, and hardcodes `payment_method_types => [ 'card' ]` for native charge/setup requests. H19 must introduce a provider-owned, server-authoritative allowed-types path; a frontend setting or filter that adds `amazon_pay` must not be enough to make native send Amazon to WPCOM.
- 2026-06-17 23:03: Both reference and native maps agree product-page ECE should be a later dedicated slice. Reference product support includes eligibility matrices, product/variation/quantity data, isolated Store API cart sessions, tokenized-cart headers, ephemeral-cart cleanup, and compatibility shims for product page add-ons/bundles/subscriptions. Native currently has no product hook, no product config, no isolated session handler, and no product cart preparation. Treating product ECE as just another placement would be a regression risk.
- 2026-06-17 23:03: Pay-for-order is a reasonable H19 candidate if implemented with its own guardrails. Reference gates on a valid order-pay query var and non-empty billing email, emits `order_id`, `pay_for_order`, `key`, and `billing_email`, disables wallet shipping changes for this context, reads `/wc/store/v1/order/{id}`, and submits `/wc/store/v1/checkout/{id}` with the order key and billing email. Native already has the Store API order route, but ECE does not hook the order-pay template, does not preserve `pay_for_order`, and always posts cart checkout. H19 should add pay-for-order as a first-class classic ECE context or leave it explicitly fail-closed.
- 2026-06-17 23:03: Tracks parity needs method specificity. Reference shopper-side ECE Tracks found in this pass cover Apple Pay and Google Pay load/click events; no shopper-side Amazon Pay Tracks event was found. Native should not record both Apple Pay and Google Pay for a single ECE ready/click path, and should not invent Amazon shopper Tracks without reference evidence.

## H19 Decision

H19 should cover the larger coherent chunk of remaining cart/checkout/order-pay ECE parity: server-validated express payment method types, Amazon Pay eligibility/config for existing cart and checkout surfaces, and classic pay-for-order ECE using the existing Store API order routes. Product-page ECE remains fail-closed for a dedicated follow-up because its isolated cart/session/product compatibility contract is materially larger and cannot be safely folded into this slice without half-building the surface.

The verification posture for H19 is: unit/Jest tests for server allowlisting and request-data propagation; classic and Blocks frontend tests for Amazon method config and pay-for-order checkout routing; browser/source evidence that assets remain split and conditional; local e2e where Stripe/account/browser availability permits; and honest limitation notes where Amazon wallet runtime availability cannot be made deterministic locally.

## Implementation Notes

- 2026-06-17 23:43: Native now owns ECE Stripe method types through `WooPaymentsExpressPaymentMethodTypes`. Payment request maps to `card`; Amazon maps to `amazon_pay` only when the feature flag is on, ECE confirmation tokens are enabled, the merchant enabled Amazon in `upe_enabled_payment_method_ids`, account data has active `amazon_pay_payments` capability and `amazon_pay` fees, the currency is supported for the account country, and billing-address tax is not in use except for pay-for-order.
- 2026-06-17 23:43: Runtime inspection showed both reference and target stores do not persist `upe_available_payment_methods` in gateway settings. The native helper was corrected to treat that option as an optional explicit deny/allow list when present, and otherwise derive availability from cached account capability/fees like the reference gateway path does.
- 2026-06-17 23:43: Native service now filters localized `enabled_methods` so stale configured `amazon_pay` is removed unless the server allowlist also permits Stripe `amazon_pay`. Classic and Blocks frontend guards also require `payment_method_types` to include `amazon_pay`, preventing JS from resurrecting Amazon from stale method IDs.
- 2026-06-17 23:43: Classic pay-for-order support is implemented as a separate `pay_for_order` context. The controller enqueues/renders on `woocommerce_pay_order_before_payment`, service emits order id/key/billing email only after WooCommerce capability/session checks pass, and classic JS uses `/wc/store/v1/order/{id}` plus `/wc/store/v1/checkout/{id}` with the order key and billing email rather than the cart checkout route.
- 2026-06-17 23:43: Product-page ECE remains intentionally fail-closed. No native product-page hook or isolated Store API cart/session contract was added in H19.

## Review Fixes

2026-06-18 00:04 update: The first focused review gate returned source-backed blockers, all now fixed with tests. The provider helper no longer merges cart and checkout settings when validating a requested context; `pay_for_order` maps to checkout settings while preserving the `pay_for_order` context for tax and request validation. The native adapter now reads `express_checkout_context` from provider data instead of hard-coding checkout, and classic/Blocks ECE submit `wcpay-express-checkout-context` alongside `wcpay-express-payment-method-types`. Pay-for-order localization now uses the order currency for Amazon eligibility, and the billing-address tax exclusion is gated by `wc_tax_enabled()` and skipped for pay-for-order. Classic ECE startup now allows Amazon-only configurations through `isPaymentRequestEnabled() || isAmazonPayEnabled()`.
