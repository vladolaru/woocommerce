# H20 Product-Page Express Checkout Analysis

> **Prompt:** "Make sure you don't over-index on what is reliably measurable. Best to be honest about the possibilities and not chase unreliable numbers. Or at least use them honestly as stop gaps for big deltas in performance to inform that we may be doing something wrong, if their variability is high. But give it a good shot first."

## Initial Posture

H19 intentionally left product-page ECE fail-closed because the reference behavior is not a button placement toggle. The reference product-page path creates an isolated Store API cart session, adds the selected product/variation/quantity into that cart, then drives tokenized cart checkout without mutating the shopper's real cart. H20 should only proceed if the native implementation can port that contract cleanly through provider-owned WooPayments abstractions while preserving split asset loading and current cart/checkout/order-pay ECE behavior.

The measurement stance for this slice follows the user's latest instruction. Bundle presence, bundle deltas, conditional loading, build output, and Store API/header behavior are reliable gates. Local browser timings and query/timing probes are useful only as stop-gap smoke signals for large deltas unless repeatability can be demonstrated; they should not be presented as precise performance proof.

## Source Notes So Far

- H19 source map recorded the key reference contract: `WC_Payments_Payment_Request_Session` swaps the WooCommerce session handler only when `X-WooPayments-Tokenized-Cart-Session-Nonce` verifies, emits `X-WooPayments-Tokenized-Cart-Session`, supports ephemeral-cart cleanup, and protects the shopper's real cart on order-received redirects. Reference JS uses `ExpressCheckoutCartApi.useSeparateCart()` and `addProductToCart()` only for product pages.
- Current native Core already localizes `tokenized_cart_session_nonce` and has frontend branches for product headers, but the controller does not register a product-page display hook, `product` config is empty, there is no native tokenized/session handler, and no native frontend product add-to-cart path exists for ECE.
- The likely implementation surface is broader than `WooPaymentsExpressCheckoutController`: it probably needs a native payment-request session service/controller, product config in `WooPaymentsExpressCheckoutService`, classic product-page frontend handling in `woopayments-express-checkout.js`, and focused tests around isolation/fail-closed behavior.

## Reference Contract Anchors

- Product-page detection and method settings are context-specific in `includes/express-checkout/class-wc-payments-express-checkout-button-helper.php`: product pages include `is_product()` or `[product_page]` shortcode content, context maps to `product`, and `express_checkout_product_methods` controls product placement while `pay_for_order` maps to checkout settings.
- Reference product eligibility is broader than a simple product-only gate. It blocks unsupported product types, pre-orders charged on release, composites and mix-and-match on product pages, free-trial subscriptions without a sign-up fee, file-upload add-ons, zero-price products, unsupported cart item types, multiple shipping packages, and non-shipping products when tax is billing-address based and prices exclude tax.
- Product config comes from `get_product_data()`: it resolves default or query-selected variable product attributes, tries matching variations, calculates display price and tax like cart display, adds pending shipping when shipping is needed, and returns `displayItems`, `total`, `needs_shipping`, `currency`, `country_code`, and `product_type`. Bundle product server data is deliberately treated as unreliable by frontend code and refetched through the Store API.
- Reference display wiring uses `WC_Payments_Express_Checkout_Button_Display_Handler::init()` to hook `woocommerce_after_add_to_cart_form` at priority 1, cart, checkout, and order-pay. The rendered wrapper includes `#wcpay-express-checkout-element`, `#wcpay-express-checkout-button-separator`, and order-attribution inputs.
- Reference isolated-cart server handling lives in `includes/class-wc-payments-payment-request-session.php` plus `includes/class-wc-payments-payment-request-session-handler.php`. It filters `woocommerce_session_handler` at priority 20 only for Store API requests with a valid `X-WooPayments-Tokenized-Cart-Session-Nonce`, validates any provided `X-WooPayments-Tokenized-Cart-Session` JWT, disables persistent cart merge, adds an order-received URL marker, emits an updated `X-WooPayments-Tokenized-Cart-Session` response header, and deletes the ephemeral tokenized cart when `X-WooPayments-Tokenized-Cart-Is-Ephemeral-Cart: 1` is present.
- Reference frontend product flow is in `client/express-checkout/cart-api.js`, `client/express-checkout/shortcode-buttons-express/index.js`, and `client/express-checkout/shortcode-buttons-express/compatibility/wc-product-page.js`. It uses `useSeparateCart()` for product pages, prefetches an ephemeral add-item cart for initial data, blocks checkout when the product variation/add-to-cart state is incomplete, calls `/wc/store/v1/cart/add-item` before resolving the payment sheet, waits for add-item before shipping-address updates, empties the isolated cart on cancel/error, and preserves selected classic/IAPI variation attributes through the `wcpay.express-checkout.cart-add-item` filter.

## Native Gap Anchors

- `WooPaymentsExpressCheckoutService` already accepts `product` as a normalized context and can return `should_show_payment_request_button( 'product' )` when `express_checkout_product_methods` contains `payment_request`, but `get_express_checkout_params()` currently emits `product => array()` and does not enforce product-page eligibility beyond provider readiness and method settings.
- `WooPaymentsExpressCheckoutController` registers checkout, cart, and pay-for-order hooks only. It does not hook `woocommerce_after_add_to_cart_form`, does not recognize product or `[product_page]` surfaces, and `get_current_button_context()` falls back to checkout unless cart/order-pay are detected.
- `plugins/woocommerce/client/legacy/js/frontend/woopayments-express-checkout.js` has partial product scaffolding: Store API cart requests include `X-WooPayments-Tokenized-Cart-Session-Nonce` when `button_context` is `product`, and checkout sends `X-WooPayments-Tokenized-Cart: true`. It lacks a cart-token/session carry-forward header, `useSeparateCart()`, `/cart/add-item`, variation/quantity collection, add-to-cart blocking, ephemeral cleanup, product refresh, and shipping address/rate update handlers equivalent to the reference.
- Core has `Automattic\WooCommerce\StoreApi\Utilities\JsonWebToken` and `CartTokenUtils`, plus `Automattic\WooCommerce\StoreApi\SessionHandler`, but the Store API handler activates only for valid `Cart-Token`. It does not create a new isolated cart when a WooPayments product-page ECE session nonce is present, so H20 still needs a provider-owned tokenized cart session controller/handler unless a broader Core Store API abstraction is introduced.
- The classic ECE script and CSS are already normal Core frontend assets through `WC_Frontend_Scripts`, and Blocks ECE is a separate block-library entry. H20 should extend these existing split bundles and avoid loading product-page ECE assets when product placement is not eligible.

## Subagent Reconciliation

- The native-state explorer independently confirmed that `WooPaymentsExpressCheckoutService` treats `product` as a context but emits no product payload, while `WooPaymentsExpressCheckoutController` and the Blocks integration gate surfaces to cart/checkout/order-pay only. It also confirmed Store API add-item and checkout data plumbing are reusable, but no Core-native consumer currently interprets `X-WooPayments-Tokenized-Cart*` headers.
- The reference-contract explorer produced the detailed source map now preserved in `analysis-h20-reference-product-ece-contract.md`. The must-port set matches the inline findings here: product hook priority 1, `#wcpay-express-checkout-element`, product eligibility/config, Store API add-item with variation/quantity data, tokenized isolated cart headers/nonces, cancel/error cleanup, order-received real-cart protection, relevant compatibility shims, Tracks parity, and ECE styling.
- Both explorer outputs support the same architecture decision: product-page card/wallet ECE should not be implemented through WooPay. It needs a sibling WooPayments express-checkout path with a provider-level tokenized cart session abstraction that can later serve other WooPayments-provided payment methods if needed.

## Scope Recommendation

H20 should close native product-page ECE for the reference core product-page contract: simple products, variable products with selected/default attributes, product-page hook/rendering, product config, isolated Store API cart session, add-item before payment-sheet resolution, cancel/error cleanup, and real-cart protection on order-received. It should preserve reference extension/filter seams for cart-add-item data and product eligibility, but any complex product extension that cannot be deterministically recreated locally should be fail-closed or source-dispositioned rather than claimed as fully e2e-covered.

The implementation should not use WooPay as the abstraction owner. Product-page card wallets/Amazon ECE remain sibling WooPayments-provided platform payment methods, owned by `WooPaymentsExpressCheckoutService`/controller/session code. If the session handler proves reusable by other WooPayments-provided payment methods later, expose it behind a narrow provider-level API instead of spreading header parsing through frontend code.

## Implementation Evidence

Current H20 implementation adds product-page ECE at the native WooPayments provider level rather than under WooPay. The source changes add a tokenized cart session controller and handler, product-page eligibility/config in `WooPaymentsExpressCheckoutService`, product rendering/enqueue support in `WooPaymentsExpressCheckoutController`, product-aware classic ECE frontend flow, and focused PHP/Jest coverage for isolated sessions, product add-item, token carry-forward, amount updates, cleanup, and product-page rendering.

The stale blocker list from earlier H20 reviewers was rechecked against current source before final review: invalid incoming session tokens are rejected through `woocommerce_rest_invalid_tokenized_cart_session` while still using the tokenized handler instead of falling back to the real cart; tokenized sessions now generate `t_` IDs even for logged-in shoppers; the canonical classic ECE registration depends on `wp-hooks`; product types fail closed to `simple`, `variable`, and `variation` unless filtered; shortcode product pages are detected through queried object/get-post fallbacks; Elements is updated after Store API add-item returns a changed total; and cleanup uses the ephemeral tokenized session header instead of recursively removing cart items.
