## Strengths

The checkout gate has a useful fail-closed core: it records required selector/resource/settings/global/token checks, non-ignored failed responses, non-ignored console issues, page errors, screenshots, and partial evidence after each route, then throws when any result fails. The admin gate similarly validates route tokens, target chunk loading, target navigation, console/page errors, and failed responses, and both scripts reject unknown surface/viewport/store filters instead of silently doing no work.

Both saved evidence files are complete and broad for this run: checkout finished with 24/24 route checks passing across 6 surfaces, 2 stores, and 2 viewports; admin finished with 57/57 route checks passing across 14 surfaces plus target navigation, 2 stores, and 2 viewports.

## Findings

### High: Admin protected routes can pass while the target route is unavailable

Source-backed and evidence-backed. `isTargetSurfaceAvailable()` treats `allowedRoutes[path] === false` as unavailable, but `checkRoute()` then swaps the expected content tokens for the generic unavailable-route token, suppresses expected-token failures via `unmetRequiredTokens = targetSurfaceAvailable && strictTokens ? missingTokens : []`, suppresses missing target assets while unavailable, and still marks the check passed when only `unavailableTokenMissing`, `forbiddenTargetAssets`, network, console, and page errors are clear (`tools/woopayments-merge/a4-admin-browser-gate.playwriter.mjs:285`, `tools/woopayments-merge/a4-admin-browser-gate.playwriter.mjs:360`, `tools/woopayments-merge/a4-admin-browser-gate.playwriter.mjs:366`, `tools/woopayments-merge/a4-admin-browser-gate.playwriter.mjs:371`, `tools/woopayments-merge/a4-admin-browser-gate.playwriter.mjs:405`). The saved evidence shows target `documents`, `card-readers`, and `capital` all had their expected tokens missing, `targetSurfaceAvailable: false`, no scripts/resources loaded, and `passed: true` (`.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq-admin-browser-gate.json:1292`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq-admin-browser-gate.json:1300`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq-admin-browser-gate.json:1327`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq-admin-browser-gate.json:1342`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq-admin-browser-gate.json:1502`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq-admin-browser-gate.json:1510`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq-admin-browser-gate.json:1537`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq-admin-browser-gate.json:1552`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq-admin-browser-gate.json:1602`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq-admin-browser-gate.json:1609`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq-admin-browser-gate.json:1636`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq-admin-browser-gate.json:1651`). For a parity gate, this can mask regressions where a route is incorrectly removed from availability, especially because the account state in evidence is `full` while those routes are unavailable. Recommendation: treat target route unavailability as a failed check for surfaces included in `selectedSurfaces`, or explicitly mark those surfaces skipped/non-passing with a required reason and exclude them from green parity counts.

### Medium: Express-checkout UI checks only require one of the core express element or WooPay button

Source-backed; current evidence shows the issue did not occur in this run. The checkout gate config groups `.wcpay-core-express-checkout__element` and `.woopay-express-button` together for `blocks-checkout-express` and `blocks-cart-express`, and `collectAnySelectorEvidence()` marks the group passed when any selector passes (`tools/woopayments-merge/a4-checkout-browser-gate.playwriter.mjs:86`, `tools/woopayments-merge/a4-checkout-browser-gate.playwriter.mjs:118`, `tools/woopayments-merge/a4-checkout-browser-gate.playwriter.mjs:381`). That means the gate would stay green if the native core express element stopped rendering but the WooPay button remained visible, or vice versa. The evidence currently shows both target selectors visible on desktop checkout and cart (`.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq/a4aq-checkout-browser-gate.json:1821`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq/a4aq-checkout-browser-gate.json:1826`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq/a4aq-checkout-browser-gate.json:1832`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq/a4aq-checkout-browser-gate.json:3542`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq/a4aq-checkout-browser-gate.json:3547`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq/a4aq-checkout-browser-gate.json:3553`), but the source assertion is looser than the regression it is meant to catch. Recommendation: split the group into separate required checks for the core express element and WooPay where both are expected by the fixture, or add per-method expected/optional metadata so a missing method cannot be hidden by another visible button.

### Medium: Checkout known-noise filtering ignores target-side `useSelect` warnings globally

Source-backed and evidence-backed. The checkout gate classifies console messages containing `error|warning|fatal|exception` as issues, but then ignores the `useSelect` warning for every store and surface (`tools/woopayments-merge/a4-checkout-browser-gate.playwriter.mjs:306`, `tools/woopayments-merge/a4-checkout-browser-gate.playwriter.mjs:310`, `tools/woopayments-merge/a4-checkout-browser-gate.playwriter.mjs:315`). The admin gate is stricter here and ignores `useSelect` only for the reference store (`tools/woopayments-merge/a4-admin-browser-gate.playwriter.mjs:233`, `tools/woopayments-merge/a4-admin-browser-gate.playwriter.mjs:238`). The checkout evidence contains target-side ignored `useSelect` warnings on blocks checkout, including 20 ignored target warnings on desktop card, 20 on desktop express, 27 on mobile card, and 27 on mobile express; the JSON line evidence shows target checkout warnings from `store8889.localhost` being recorded as ignored (`.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq/a4aq-checkout-browser-gate.json:1169`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq/a4aq-checkout-browser-gate.json:1175`). This can mask target-specific regressions if native WooPayments introduces a new unstable selector warning in checkout. Recommendation: make target console filtering evidence-aware and bounded by exact known owner/source/surface, or require target-side warning parity against the reference rather than blanket-ignore.

### Medium: Checkout target/reference evidence is not fixture-normalized, so green parity can depend on stale browser/cart state

Source-backed and evidence-backed. The checkout gate reuses an existing Playwriter page/context when present, only navigates to `about:blank`, and does not clear cookies, storage, cart session, or logged-in/customer state before checking routes (`tools/woopayments-merge/a4-checkout-browser-gate.playwriter.mjs:346`, `tools/woopayments-merge/a4-checkout-browser-gate.playwriter.mjs:529`). It also stores only `expressCheckoutMethods` from Store API responses in the normalized `storeApiResponses`, while pass/fail is based on per-store tokens/selectors/resources/settings without comparing target and reference fixture facts (`tools/woopayments-merge/a4-checkout-browser-gate.playwriter.mjs:613`, `tools/woopayments-merge/a4-checkout-browser-gate.playwriter.mjs:645`, `tools/woopayments-merge/a4-checkout-browser-gate.playwriter.mjs:661`). The saved evidence shows materially different target/reference checkout fixtures while still reporting pass: target desktop blocks checkout has `cartTotal: 17170`, `storeCountry: US`, and methods `amazon_pay`, `payment_request`, `woopay`; reference has `cartTotal: 34702`, `storeCountry: GB`, and methods `amazon_pay`, `payment_request` (`.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq/a4aq-checkout-browser-gate.json:241`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq/a4aq-checkout-browser-gate.json:242`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq/a4aq-checkout-browser-gate.json:1273`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq/a4aq-checkout-browser-gate.json:1458`, `.agents/scratchpad/sessions/2026-06-15-core-native-payments/data/a4aq/a4aq-checkout-browser-gate.json:1494`). That makes the run useful as smoke evidence, but weak as reference parity evidence; country, cart contents, totals, logged-in state, and enabled methods can all change express/card availability and layout. Recommendation: add a fail-closed fixture preflight that records and compares normalized target/reference cart facts before route checks, or explicitly label the evidence as smoke-only when fixture facts differ.

## Residual Coverage Limits

The saved checkout gate does not submit card payments, setup intents, WooPay, ECE wallet flows, 3DS/SCA, order-pay, order attribution, BNPL/local payment-method field parity, or visual-diff/styling parity beyond selector/resource/screenshot artifacts. The admin gate is token/chunk/navigation evidence, not deep interaction coverage for filters, exports, dispute flows, settings mutations, report table correctness, or account-feature entitlement correctness. I did not rerun the browser gates because this review was scoped to source and saved evidence; I only ran syntax checks.
