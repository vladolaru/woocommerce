## Findings

### High: Playwriter state and local-only validation can let the gate run the wrong store or skip required admin coverage

If a reused Playwriter session has `state.targetBase`, `state.referenceBase`, `state.routes`, or `state.skipNavigation` set from a prior probe, the A4aq orchestrator only clears `surfaceIds`, `viewportIds`, and `storeIds` before running the browser gates (`a4aq-accumulated-gate.py:246-248`; aggregate evidence records the exact cleanup command at `a4aq-accumulated-gate.json:35-37`). The checkout gate trusts those remaining `runState` values for target/reference base URLs and per-surface route overrides (`a4-checkout-browser-gate.playwriter.mjs:12-35`), including absolute URLs through `localUrl()` (`a4-checkout-browser-gate.playwriter.mjs:27-30`), while the admin gate also allows a stale `state.skipNavigation === true` to bypass the target navigation assertion (`a4-admin-browser-gate.playwriter.mjs:478-479`). The preflight local-only guard is also not sufficient: it joins all arguments and rejects forbidden hosts only when the whole joined string does not contain `localhost` (`a4aq-accumulated-gate.py:112-114`), so a remote `wordpress.com` target can pass as soon as any other argument includes a localhost URL. Failure mode: the accumulated gate can visit a stale route set, a remote URL, or skip target admin navigation, then emit successful child evidence for the wrong coverage surface. Detection gap: the orchestrator records child exit codes but does not validate requested browser hosts or forbidden state keys after the Playwriter cleanup. Blast radius: A4aq can certify checkout/admin parity while not exercising the intended target store, and target warnings/errors on the real store would never be observed. Confidence: 90.

Recommendation: reset the Playwriter session to a known allowlisted state before the browser gates, including deleting or explicitly setting `targetBase`, `referenceBase`, `routes`, `skipNavigation`, and any retained `page`/context handles. Validate each WP command argument and every requested browser URL independently with a URL parser and an explicit local-host allowlist; do not use a joined-string `localhost` exception. After each child browser gate, parse evidence and fail closed if any `requestedUrl` or `finalUrl` is outside the expected local hosts, or if required checks such as admin navigation were skipped.

### High: Checkout warning/error classification ignores target warnings and can miss console errors entirely

The checkout gate identifies console issues by searching message text for `error|warning|fatal|exception` (`a4-checkout-browser-gate.playwriter.mjs:306-308`) instead of treating `message.type() === "error"` or `"warning"` as sufficient. It then ignores broad warning classes without store or surface scoping, including WooCommerce dependency warnings, `useSelect` warnings, Amazon Pay fetch failures, Stripe HTTPS/domain warnings, and localhost Apple Pay domain warnings (`a4-checkout-browser-gate.playwriter.mjs:310-318`); failed-response ignores are also global for Stripe telemetry 400s, WooPay user-exists 429s, and Amazon Pay merchant-id 500s (`a4-checkout-browser-gate.playwriter.mjs:291-303`). The handler moves matching target messages into `ignoredConsoleIssues` (`a4-checkout-browser-gate.playwriter.mjs:556-565`), and pass/fail only considers non-ignored `consoleIssues`/`failedResponses` (`a4-checkout-browser-gate.playwriter.mjs:661-665`). The captured A4aq evidence proves the fail-open behavior: target `blocks-cart-express` mobile recorded ignored target warnings, including `[WooCommerce] An inline or unknown script accessed wc.wcBlocksData without proper dependency declaration...` (`a4aq-checkout-browser-gate.json:11423-11430`), yet the same result is marked `passed: true` (`a4aq-checkout-browser-gate.json:11437-11439`) and the child gate has `failures: []` (`a4aq-checkout-browser-gate.json:13496-13497`). Failure mode: a target checkout warning caused by the native WooPayments integration, or a `console.error()` whose text does not include the hardcoded keywords, can be hidden while the orchestrator records the checkout browser check as passed. Detection gap: ignored target warnings remain inside child evidence but do not affect the child exit code or aggregate status. Blast radius: shopper-facing checkout regressions can be present in the browser console while A4aq reports green browser coverage. Confidence: 88.

Recommendation: classify by console message type first, then apply exact allowlist rules keyed by store, surface, viewport, and message text. Default target warnings/errors to failures; if a local-environment warning must be tolerated, require an explicit `expectedTargetWarnings` entry on that surface and include ignored-target counts in aggregate evidence. Keep reference-only noise reference-scoped, and make target ignored failed responses fail or at least mark the run incomplete unless the surface declares the exact expected URL/status.

### Medium: Log scan evidence is not anchored to the run window or the WP commands under test

`scan_logs()` computes a `since_arg` for `docker logs` (`a4aq-accumulated-gate.py:405-417`), but reads the full WordPress `debug.log` with `cat` and no timestamp filter (`a4aq-accumulated-gate.py:419-420`). The aggregate evidence shows the scan window was `2026-06-20T11:50:27Z` (`a4aq-accumulated-gate.json:295-296`) while `debug_diagnostics` contains stale reference entries from `09:07`, `09:53`, and `11:24` (`a4aq-accumulated-gate.json:257-264`). The same code path would fail the target gate on stale target `debug.log` lines from earlier runs, or hide current target logs if `docker exec` fails, because `run_text()` discards command exit codes and returns stdout/stderr as plain text (`a4aq-accumulated-gate.py:467-469`). The container lookup is also hard-coded to the first `docker ps` entry exposing `:8889->` for target and exact `wcpay_wp_default` for reference (`a4aq-accumulated-gate.py:411`, `a4aq-accumulated-gate.py:448-457`), rather than deriving or validating the web containers from `--target-wp`/`--ref-wp`. Failure mode: the log scan can pass while scanning the wrong or unreadable logs, or fail due to stale target warnings unrelated to the current A4aq run. Detection gap: aggregate evidence records the chosen container but not Docker command success, debug-log timestamp filtering, or a proof that the selected container corresponds to the WP commands used by perf/source gates. Blast radius: on-call-style diagnosis from the aggregate file can be misleading, especially when deciding whether target warnings/errors were actually absent. Confidence: 82.

Recommendation: snapshot/truncate debug logs at preflight or filter `debug.log` entries by parsed timestamp >= `started_at`; treat any `docker logs`/`docker exec` nonzero exit as `incomplete` with stderr captured separately. Resolve target/reference web containers from the WP command, Docker Compose project labels, or verified site URLs, and record that validation in evidence before accepting a clean log scan.
