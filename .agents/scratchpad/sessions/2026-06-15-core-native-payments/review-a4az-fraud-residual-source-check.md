## Answer

Yes, fraud ruleset GET/refresh/defaulting is still a source-backed native gap after A4ay. A4ay closed the tour and tracking gap, and native now records advanced save/card-view events, but native still does not fetch the latest server fraud ruleset, does not infer the current protection level from the server ruleset, does not save Basic to the server when the platform reports no ruleset, and does not expose the reference-style fetch-error state from the backend settings contract.

Yes, advanced fraud loading/card-detail parity is still source-backed. Native has the seven cards, route, save flow, and A4ay tracking, but it still renders a single plain loading status instead of reference-style page/card skeletons and still lacks multiple merchant-facing details in the rule cards: linked selling-location/IP/supported-country copy, the allowed-countries informational notice, currency-prefixed purchase amount inputs, "Leave blank for no limit" helper text, inline threshold warning/error notices, stricter item input affordances, and reference-style toggle/card notice treatment.

The next bounded slice should be fraud ruleset GET/refresh/defaulting, including the related "selling locations changed" ruleset refresh. It is the better throughput/risk slice because it is backend-contract-sized, testable with focused PHP and API-client unit tests, and fixes the source-of-truth foundation that every fraud UI reads. The card-detail/loading slice is visible and worthwhile, but it is broader frontend polish with more visual/copy surface; it should follow once native is no longer at risk of showing or saving stale fraud configuration.

## Q1: Ruleset GET, Refresh, And Defaulting

## Recommended Next Slice

Implement A4az as "fraud ruleset source refresh/defaulting parity." Bound it to backend settings/API behavior and focused tests: add a native `get_latest_fraud_ruleset()` API-client method for the existing fraud ruleset endpoint; add a run-once refresh helper to the settings service; call it before returning the current protection level and advanced fraud settings; cache fetched `ruleset_config`; update `current_protection_level` by matching Basic/Standard/High/Advanced rulesets; on `wcpay_fraud_ruleset_not_found`, save the Basic empty ruleset to the platform, set the transient, and set the level to `basic`; on other fetch failures, expose the `'error'` advanced-settings state so the existing frontend disabled/error paths are backed by real server behavior.

Include the small adjacent sync if it stays within the same patch: when WooCommerce General selling locations change and the current level is Advanced, update the saved international-IP rule check to the current selling-location operator/value and save/cache it. This is source-backed reference behavior and prevents a subtle merchant-facing mismatch where the UI shows current allowed countries but the saved platform rule can still carry old country values.

Defer the advanced loading/card-detail slice until after the backend source-of-truth slice. That follow-up should be a frontend-focused A4ba-style patch with targeted Jest expectations for skeleton/loading shape, allowed-country notices, linked AVS/IP/supported-country copy, purchase amount currency prefixes and helper text, inline threshold warning/error notices, order item input restrictions, and no regression to the rule-specific filter-action accessible names.
