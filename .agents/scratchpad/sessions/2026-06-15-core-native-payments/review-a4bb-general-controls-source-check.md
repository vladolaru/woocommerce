## Payment Request / Express Save Telemetry Fit

The payment-request save telemetry belongs naturally in this A4bb slice if kept to the reference event and not expanded into a broader express-settings rewrite. Reference stores the initial `is_payment_request_enabled`, waits for `saveSettings()` success, then records `wcpay_payment_request_settings_change` with `enabled: 'yes' | 'no'` only when the saved setting changed (`/Users/vladolaru/Work/a8c/woocommerce-payments/client/settings/save-settings-section/index.js:28-33` and `/Users/vladolaru/Work/a8c/woocommerce-payments/client/settings/save-settings-section/index.js:59-82`). Native already exposes `is_payment_request_enabled` through the express overview row (`plugins/woocommerce/client/admin/client/woopayments/settings/settings-page.tsx:818-835`, `plugins/woocommerce/client/admin/client/woopayments/settings/settings-page.tsx:929-935`, and `plugins/woocommerce/client/admin/client/woopayments/settings/settings-page.tsx:1062-1069`) and already centralizes save success handling in `SaveSettingsSection` (`plugins/woocommerce/client/admin/client/woopayments/settings/settings-page.tsx:1879-1954`), so adding this one event there is lower-risk and source-local.

This should not pull in the full express checkout detail surfaces. Native intentionally keeps overview rows separate from express detail controls on the General page, with tests asserting detail controls are absent from the overview (`plugins/woocommerce/client/admin/client/woopayments/settings/test/settings-page.test.tsx:2370-2385`). A4bb should include only the reference save telemetry for `is_payment_request_enabled`, plus tests that it fires after successful save and not after failed save or unchanged saves.

## Recommended A4bb Scope

1. Add a native `EnableWooPaymentsCheckbox`-equivalent flow inside the General section: checkbox help copy, disable confirmation modal with affected payment methods/help links, and `wcpay_gateway_toggle` for enable/disable. Reuse existing native settings hooks and payment-method metadata rather than importing reference-only assets.

2. Add switch-to-live parity for telemetry and action state: track settings/event-bridge click, modal CTA, and modal exit; add submitted/busy state to the native setup-live modal; add tooltip learn-more affordances if the available component set supports it cleanly. If tooltip parity requires building a reusable tooltip component, keep it as a medium-priority subtask after telemetry/busy state.

3. Add test-mode Tracks parity: record enabled on modal confirm, disabled when unchecked, and modal exit on cancel/close; improve help copy/links for normal and dev-mode states to match the reference intent.

4. Add the `wcpay_payment_request_settings_change` save telemetry to native `SaveSettingsSection`, scoped only to `is_payment_request_enabled` changes after successful save.

5. Add focused tests around each parity event and destructive confirmation behavior. Existing native tests can be extended in `plugins/woocommerce/client/admin/client/woopayments/settings/test/settings-page.test.tsx`; no WPCOM sandbox, WPCOM changes, push, or scratchpad linting are needed for this source-derived slice.
