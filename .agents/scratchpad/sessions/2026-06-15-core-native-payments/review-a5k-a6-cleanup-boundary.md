# A5k A6 Cleanup Boundary Review

## Verdict

HOLD_A6_FOR_RELEASE.

A6a remains a valid future Bucket-D cleanup candidate, but it should not start while the branch is still fail-closed/default-off and while rollback/coexistence with the unmodified WooPayments extension is still part of the A5 safety model. The tighter source-backed reason is not generic conservatism: removing the deprecated bundled-subscriptions settings surface now would change merchant-facing and rollback-adjacent behavior for stores that still have `_wcpay_feature_subscriptions=1`. Current native Core mirrors the standalone plugin's disable-only contract: it exposes the flag, renders the deprecated settings control, and allows turning the old flag off but not on. The standalone plugin still reads that same option to decide whether to load `subscriptions-core` and whether bundled/Stripe Billing subscription behavior is present. Until mandatory/default-on/release sequencing ends the plugin-active rollback window, deleting Core's disable/signpost surface leaves stale plugin-owned state intact and removes a merchant-visible path that currently exists.

It also records the reconciliation tension: `review-a6-bucket-d-source-audit.md` says this is the future clear first slice, but `review-a6-boundary-audit.md` controls sequencing and says product cleanup remains held (`analysis-a6-replanned-cleanup-readiness.md:48-56`).

`review-a6-boundary-audit.md` held A6 product cleanup because A5 mandatory/default-on was not complete, canonical A6 is downstream of A5, Bucket D subscription cleanup is gated by Bucket C/E preservation and Stripe Billing data safety, and product source still has cutover-blocking legacy Stripe Billing marker guards (`review-a6-boundary-audit.md:21-39`). ## Current Core Source

Core backend settings still define the deprecated option and expose it in the native settings contract: `WooPaymentsSettingsService::WCPAY_SUBSCRIPTIONS_FLAG_OPTION = '_wcpay_feature_subscriptions'`, `get_settings()` returns `is_wcpay_subscriptions_enabled`, `is_wcpay_subscriptions_eligible`, and `is_subscriptions_plugin_active`, and `update_settings()` writes the option to `0` when `is_wcpay_subscriptions_enabled=false` is posted (`plugins/woocommerce/src/Internal/Payments/Providers/WooPayments/WooPaymentsSettingsService.php:29`, `:265-281`, `:587-593`). The helper only checks whether Subscriptions runtime classes exist; it does not drive native renewal processing (`plugins/woocommerce/src/Internal/Payments/Providers/WooPayments/WooPaymentsSettingsService.php:1775-1782`).

The native settings REST controller still accepts the update key (`plugins/woocommerce/src/Internal/Admin/Settings/PaymentsProviders/WooPayments/WooPaymentsRestController.php:766-782`). The admin store exposes the action/selectors/hook for the old setting (`plugins/woocommerce/client/admin/client/woopayments/settings/data/actions.ts:145-152`, `plugins/woocommerce/client/admin/client/woopayments/settings/data/selectors.ts:197-206`, `plugins/woocommerce/client/admin/client/woopayments/settings/data/hooks.ts:170-184`).

The current merchant-facing UI is not purely dead text. `AdvancedSettingsSection` calls `useWCPaySubscriptions()` and renders `Enable Subscriptions with WooPayments`; for an eligible store with the option already enabled, the checkbox is not disabled because `disabled={! isWCPaySubscriptionsEligible || ! isWCPaySubscriptionsEnabled}`. Its handler ignores attempts to enable but calls `setIsWCPaySubscriptionsEnabled(false)` when unchecked (`plugins/woocommerce/client/admin/client/woopayments/settings/settings-page.tsx:2123-2134`, `:2172-2214`). Existing tests assert the deprecation copy and that enabling is prevented (`plugins/woocommerce/client/admin/client/woopayments/settings/test/settings-page.test.tsx:4283-4340`); backend tests assert the flag is exposed and can be written to `0` while Stripe Billing remains untouched (`plugins/woocommerce/tests/php/src/Internal/Payments/Providers/WooPayments/WooPaymentsSettingsServiceTest.php:260-276`, `:890-936`, `:2045-2062`).

Native WC Subscriptions integration is already independent of the deprecated flag and must be preserved. `NativeWooPaymentsGateway::is_subscriptions_enabled()` checks the standalone WC Subscriptions plugin/core runtime, not `_wcpay_feature_subscriptions`; the gateway adds subscription support flags, registers renewal/failing-payment hooks, and adds failed-renewal authentication emails when Subscriptions runtime is available (`plugins/woocommerce/src/Internal/Payments/NativeWooPaymentsGateway.php:541-547`, `:938-991`, `:1003-1015`). Token propagation to related subscriptions is handled by `WooPaymentsTokenService`, the provider gateway adapter, and the checkout AJAX controller (`plugins/woocommerce/src/Internal/Payments/Providers/WooPayments/WooPaymentsTokenService.php:257-339`, `plugins/woocommerce/src/Internal/Payments/Providers/WooPayments/WooPaymentsProviderGatewayAdapter.php:924-965`, `plugins/woocommerce/src/Internal/Payments/Providers/WooPayments/WooPaymentsCheckoutAjaxController.php:651-669`). Existing tests protect the fact that deprecated Stripe Billing flags do not control native subscription support or tokenized renewals (`plugins/woocommerce/tests/php/src/Internal/Payments/NativeWooPaymentsGatewayTest.php:184-214`, `:390-422`) and protect token sync for recurring flows (`plugins/woocommerce/tests/php/src/Internal/Payments/Providers/WooPayments/WooPaymentsProviderGatewayAdapterTest.php:1907-1998`, `plugins/woocommerce/tests/php/src/Internal/Payments/Providers/WooPayments/WooPaymentsCheckoutAjaxControllerTest.php:504-597`).

The Stripe Billing data-safety guard must remain untouched. `WooPaymentsLegacySubscriptionsGuard` searches HPOS and CPT storage for legacy WCPay/Stripe Billing subscription and invoice marker keys and answers whether native cutover would strand data (`plugins/woocommerce/src/Internal/Payments/Providers/WooPayments/Subscriptions/WooPaymentsLegacySubscriptionsGuard.php:31-67`, `:83-120`). `WooPaymentsCutoverController` adds `legacy_stripe_billing_subscriptions_present` after filters, so callers cannot filter the blocker away, and the blocked notice instructs merchants to install WooCommerce Subscriptions and run the WooPayments Stripe Billing migration from the extension (`plugins/woocommerce/src/Internal/Payments/Providers/WooPayments/WooPaymentsCutoverController.php:451-456`, `:723-730`). Tests cover active, cancelled, migrated, invoice, HPOS, filter-resistant, clean-store, notice, and mandatory-auto-deactivation cases (`plugins/woocommerce/tests/php/src/Internal/Payments/Providers/WooPayments/WooPaymentsCutoverControllerTest.php:675-798`).

The branch is still intentionally fail-closed: native runtime defaults false and plugin-wins while the plugin is active (`plugins/woocommerce/src/Internal/Payments/NativePaymentsRuntimeArbiter.php:86-104`, `:131-185`), and mandatory cutover defaults false (`plugins/woocommerce/src/Internal/Payments/Providers/WooPayments/WooPaymentsCutoverController.php:40-54`, `:622-630`). A5j refreshed local evidence but still records release/default-on as blocked on production/release-only evidence and keeps A6 cleanup held (`analysis-a5j-release-default-on-readiness.md:23-25`, `:84-86`).

## Standalone Plugin Rollback Evidence

Because the A5 safety model still permits the unmodified WooPayments extension to own runtime or reclaim it on rollback, the option cannot be treated as Core-only dead state yet. The local WooPayments source still defines `_wcpay_feature_subscriptions`, exposes `is_wcpay_subscriptions_enabled()`, and returns that option through the `wcpay_is_wcpay_subscriptions_enabled` filter (`/Users/vladolaru/Work/a8c/woocommerce-payments/includes/class-wc-payments-features.php:19-25`, `:71-94`). It also uses the flag to decide whether WCPay subscriptions imply Stripe Billing behavior when WC Subscriptions is absent (`/Users/vladolaru/Work/a8c/woocommerce-payments/includes/class-wc-payments-features.php:300-315`).

The standalone plugin still initializes `subscriptions-core` when WooCommerce is loaded and `WC_Payments_Features::is_wcpay_subscriptions_enabled()` is true, unless the standalone WC Subscriptions plugin/core is active (`/Users/vladolaru/Work/a8c/woocommerce-payments/woocommerce-payments.php:216-304`). Its settings REST response returns `is_wcpay_subscriptions_enabled`, `is_stripe_billing_enabled`, eligibility, and subscription-plugin state, and its update path also only allows disabling the bundled subscriptions flag by writing `0` (`/Users/vladolaru/Work/a8c/woocommerce-payments/includes/admin/class-wc-rest-payments-settings-controller.php:544-560`, `:615-621`, `:896-907`). That is the behavior Core currently mirrors.

This is the release-sequencing dependency: before mandatory/default-on settles, plugin rollback remains a designed path, and the standalone plugin still gives `_wcpay_feature_subscriptions=1` runtime meaning. Removing Core's disable-only UI/API before that point can leave an enabled legacy flag in place for the plugin path and removes a visible deprecation/migration signpost from the native settings page for exactly the stores most likely to need it.

## Answer To The Questions

Is A6a safe before release/default-on? Not under the current A5 model. It is not a data deletion, and native renewal processing does not depend on the flag, but it is still a merchant-facing behavior change and a rollback/coexistence behavior change while the branch is default-off and the plugin can still own runtime. The current source lets an already-enabled merchant disable the deprecated flag and see deprecation guidance; A6a would remove that before the release owner has ended the plugin-active transition window.

What exact local TDD/gate slice should run now if safe? None should run now because the verdict is hold. The useful action now is this source-backed boundary write-back. Running RED tests for A6a now would create a product-change path that the sequencing evidence does not support.

What source-backed reason makes this release-sequencing dependent? The reason is the combination of fail-closed/plugin-wins defaults, unmodified-plugin rollback, and the standalone plugin still reading `_wcpay_feature_subscriptions` to load and expose bundled subscriptions behavior. The Core UI/API is currently the same disable-only contract as the plugin, not an inert leftover. Release/default-on sequencing is the point where the project can decide that plugin-owned rollback/coexistence no longer requires Core to preserve that disable/signpost path.

## Future Gate Slice After Release Sequencing Clears

When a release owner clears A6 product cleanup, the local TDD slice should start by making stale behavior impossible to preserve accidentally: update `WooPaymentsSettingsServiceTest` to assert the settings contract no longer includes `is_wcpay_subscriptions_enabled`, `is_wcpay_subscriptions_eligible`, or `is_subscriptions_plugin_active`; add/adjust a backend test that posting stale `is_wcpay_subscriptions_enabled=false` is ignored and does not mutate an existing `_wcpay_feature_subscriptions` option; update the REST update args test/coverage if present so the stale key is not accepted; update settings data tests to assert no `updateIsWCPaySubscriptionsEnabled`, `getIsWCPaySubscriptionsEnabled`, `getIsWCPaySubscriptionsEligible`, `getIsSubscriptionsPluginActive`, or `useWCPaySubscriptions` export remains; update settings page tests to assert the deprecated bundled-subscriptions copy and checkbox are absent; keep gateway renewal, token-sync, cutover-guard, and retired Stripe Billing alarm tests intact.

Future verification commands should be focused and should not lint `.agents`: `pnpm --filter=@woocommerce/plugin-woocommerce test:php:env -- --filter WooPaymentsSettingsServiceTest`, `pnpm --filter=@woocommerce/plugin-woocommerce test:php:env -- --filter NativeWooPaymentsGatewayTest`, `pnpm --filter=@woocommerce/plugin-woocommerce test:php:env -- --filter 'WooPaymentsCutoverControllerTest|WooPaymentsProviderGatewayAdapterTest|WooPaymentsCheckoutAjaxControllerTest'` for the preserved Bucket-C/guard slice touched by risk, and from `plugins/woocommerce/client/admin` run the focused Jest files for settings data and settings page. Static gates after implementation should include changed-file PHP lint, PHPStan for any touched PHP production classes, exact-file ESLint/Jest/type checks for touched TS/TSX, and branch lint/changelog checks only when commit/PR work is actually requested.
