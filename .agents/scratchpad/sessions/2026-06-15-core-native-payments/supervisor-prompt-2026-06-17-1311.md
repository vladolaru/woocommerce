# Supervisor prompt — structural gap nudges (2026-06-17 13:11)

> Read-only supervisory review of the in-flight WooPayments → core native merge. These are four structural gaps that a verification harness — which only diffs the flows it is *driven* through — will not surface on its own. They are framed as roadmap and gate obligations, not implementation dictates: fill in the code your way. Per the operating model, treat every claim below as a finding to verify against source before acting on it; do not take any of it on faith. These are blind spots a driven-flow harness structurally cannot surface — not corrections.

## N1 — Make the A4→A5 interlock explicit; gate cutover on native admin surfaces

Cutover (A5) deactivates the standalone plugin, but today that plugin still *is* the entire merchant payments dashboard. Core currently has only the Settings → Payments provider row plus onboarding (`plugins/woocommerce/client/admin/client/woopayments/onboarding/`; `plugins/woocommerce/client/admin/client/settings-payments/settings-payments-woopayments.tsx` is a placeholder). The full overview / transactions / disputes / deposits / payment-details / card-readers / reports screens are still plugin-served — A4 is essentially not started. `WooPaymentsCutoverController`'s preflight checks runtime and transport readiness, but it does not check that native admin surfaces exist, so the long backfill stream could drive the store to a cutover that strands merchants without a payments dashboard.

**Ask:** (a) record the hard dependency that **A4 must land before A5's mandatory flip**, and (b) add a preflight failure for missing native admin surfaces so cutover cannot proceed while the dashboard is still plugin-owned.

**Verify:** read `WooPaymentsCutoverController` to confirm the current preflight conditions (`get_preflight_failures()` and the mandatory/soft defaults) before changing the gate.

## N2 — Put out-of-band provider-event sync on the roadmap (an A4/A5 dependency, not a permanent throw)

`WooPaymentsEventIngestor` carries a `KNOWN_UNHANDLED_EVENT_TYPES` set that it throws on: disputes (`charge.dispute.created` / `closed` / `updated` / `funds_withdrawn` / `funds_reinstated`), `charge.refunded` / `charge.refund.updated`, `invoice.paid` / `payment_failed` / `upcoming`, `account.updated` / `account.deleted`, and `wcpay.notification`. Failing closed is correct pre-cutover, because the plugin owns the webhook route while it is active. Post-cutover it becomes a real merchant-facing regression: refunds and disputes initiated from the payments dashboard (rather than from WC admin) will not sync to the WC order, notes, or emails, and account suspension is invisible. The reference plugin processes all of these.

**Ask:** schedule these event types as an A4/A5 dependency rather than an indefinite `KNOWN_UNHANDLED` throw. At minimum, disposition each type explicitly (port now, or defer-with-reason) and tie the disposition to the cutover gate so the unhandled set cannot silently outlive cutover.

**Verify:** confirm the constant and the throw path in `WooPaymentsEventIngestor`, and confirm there is genuinely no alternative native path (a webhook/admin REST controller or the operational queue service) already handling any of them, before deciding port-vs-defer per type.

## N3 — Scope non-WooPay express checkout as its own package

Native express checkout today is WooPay-only — the in-flight WooPay frontend work (`WooPaymentsWooPaySessionService::get_woopay_frontend_config()` / `get_express_checkout_params()`). Apple Pay and Google Pay (Stripe Payment Request) and Amazon Pay have no native counterpart; the reference plugin's `client/express-checkout` and `client/tokenized-express-checkout` domains are unported. This is a large, distinct shopper-facing surface (express buttons on product, cart, and checkout) that the WooPay-focused stream can pass right by.

**Ask:** confirm Apple / Google / Amazon Pay express is tracked as its own A3-family package, not assumed-covered by the WooPay frontend work.

**Verify:** grep native PHP and JS for any payment-request / Apple-Google-Amazon-Pay registration beyond WooPay to confirm the gap before scoping.

## N4 — Stop overloading `b3*`; re-map it to real stages and confirm true multi-currency B3

The `b3a`–`b3ai` packages are payments-runtime work (Workstream A, spanning A2–A5), but in the canonical plan `b3` is multi-currency **B3 cleanup**. The series ran `a3f` / `a3g` / `a3h` and then jumped to `b3x` — that is "next free slot in an existing sequence," not "a label that reflects the workstream and stage." The cost is concrete: anyone auditing against the canonical plan reads `b3*` as multi-currency cleanup (and so concludes B3 is done when it has not been touched), while simultaneously losing track of which A3/A4/A5 gates the backfill actually closed. This exact confusion had to be worked around during this review.

**Ask:** (a) stop extending `b3*` for payments work — use a dedicated backfill track (for example `H1`, `H2`, … for "harness backfill") with each entry tagged to the canonical stage-gate it strengthens, or attribute each package to `a3*` / `a4*` / `a5*` by its true stage; (b) re-map the existing `b3*` entries to their real stages in the staging-log index; and (c) report the actual status of genuine multi-currency **B3 cleanup**, which the relabel has obscured.

## N5 — Add a stage-boundary spec-conformance gate (the systemic fix behind N1–N4)

The per-package code-review gate asks "is this diff correct?" — not "does the accumulated runtime still honor this stage's spec obligations?" Spec conformance is currently folded into per-package review (via the ecosystem-integration and api-contract reviewers) rather than gated standalone, and that asymmetry is exactly how N1–N4 slipped: each is a cross-package architectural obligation that `design-spec.md`, `bc-manifest.md`, and `staging-outline.md` call for, but that no single-diff reviewer will naturally surface. The gap is not review *depth* — it is review *scope*: the continuity and architecture obligations only become checkable when a whole stage's worth of work is viewed together against the design intent.

**Ask:** at each **stage boundary** (not per package — per-package would be wasteful and would still miss the cross-package view), run a dedicated spec-conformance gate before the stage is allowed to "exit": a fresh subagent (or a small panel) that checks the stage's accumulated work against (a) the relevant `design-spec.md` sections, (b) every `bc-manifest.md` bucket disposition for the surfaces the stage touched (each row's preserve / alias / deprecate / drop actually honored, no surface left undispositioned), and (c) the `staging-outline.md` stage gate plus the non-negotiable invariants (implementation-plan §0.6: one payments runtime, Bucket-E byte-identical, Bucket-C integrations intact, per-surface perf, no money moved without verification). Make it fail-closed — a stage does not exit until this gate is green — and record its evidence in the staging log alongside the harness and code-review evidence.

**Why standalone rather than more per-package review:** per-package review already catches diff-level defects well; what it cannot see is whether the stage, as a whole, still satisfies the design. Adding scope (a stage-level spec gate) closes that, where adding more depth would not.

## N6 — Run a one-time retroactive spec-conformance baseline before starting A4/A5

The forward stage-boundary gate (N5) is the right standing process, but A1–A3 and B0–B2 are already declared "done" without ever passing it — the H1–H12 backfill remediated A3 reactively, not against a conformance checklist. Before A4/A5 begins, run the N5 gate **once, retroactively**, over the accumulated payments and multi-currency runtime: check it against `design-spec.md`, every touched-surface bucket disposition in `bc-manifest.md`, and the implementation-plan §0.6 invariants, and record the result in `staging-log.md` as the **spec-conformance baseline**.

This is not re-doing the work — keep it at the contract and architecture level, not a line-by-line re-review. The point is to establish a known-good line so every later stage gate diffs against an *audited* baseline instead of an *assumed* one.

**Ask:** run the retroactive baseline before A4/A5 stage work begins; record it in the staging log as the spec-conformance baseline; and make it fail-closed — anything it surfaces becomes a tracked slice (an `H##` package or its true canonical stage) before A4/A5 proceed.

**Verify:** as with all of these, verify any finding against source before acting on it; the A5-exit gate will re-examine much of this runtime anyway, so the baseline's job is to find what is wrong *now*, not to pre-empt that later gate.

## N7 — Close the verification-coverage gaps the baseline exposed (harden the gates, not just the code)

The N6 baseline showed that several gates recorded as "passed" are narrower than the claims they backed. This nudge is about verification *coverage*, distinct from the N1–N4 product gaps and the N5/N6 process: before A4/A5, widen these gates so the spec-conformance baseline rests on real coverage.

**(a) Extend financial reconciliation beyond refunds — highest leverage.** `financial-reconcile.sh` reconciles only the WC-side *refund* records against Stripe (confirmed at its header, `financial-reconcile.sh:5-7`), yet it self-describes as "the money-safety oracle — RULE 0 on the money path" and is recorded as "financial reconciliation passed 7/7" in every package entry. Implementation-plan §0.6 invariant #5 (no money moves without verification) and design-spec §6.3 R12 require the full matrix: charge amounts, captures and authorizations, full and partial refunds, dispute outcomes, payouts, fees, and multi-currency. Extend the reconciler to cover these (test-mode account, raw Stripe CLI source), then re-run it over the accumulated money paths as part of the baseline. Until then, treat every prior "financial reconciliation passed" as **refunds-only**, not money-safety-complete.

**(b) Add the Bucket-C / WC Subscriptions end-to-end conformance check.** The N6 baseline dispositioned Workstream A (payments) and B (multi-currency) but not C. Workstream C requires a real WC-Subscriptions renewal end-to-end on native — assert success plus correct order/meta plus renewal and failed-renewal emails — diffed against the reference. The renewal code exists (`NativeWooPaymentsGateway::scheduled_subscription_payment()`, the subscription `supports[]`), but it has never been conformance-gated. Add it to the baseline and to the standing stage gate.

**(c) Treat perf and bundle-size as *exercised*, not merely *available*.** `verify.sh` marks broad perf and bundle-size as runbook/judgment gates outside the deterministic PASS. §0.6 invariant #4 (per-surface perf preserved) needs an actual exercised measurement across the touched A3/B2 surfaces against the design-spec §5.3 baseline — not "the runbook exists." Record the numbers, or mark the invariant explicitly unverified.

**Ask:** treat each as a coverage gap that blocks a *trustworthy* A4/A5 spec gate — widen the gate, re-run it over the accumulated runtime, and record results in the staging log; make it fail-closed so a narrow gate can no longer be cited as a broad guarantee.

**Verify:** verify each against source first. Item (a) is the most urgent because it retroactively touches every money path already shipped as "done."

## N9 — Settle Stripe Billing in one holistic slice (retire cleanly, gated on data-safety)

> This formalizes the H31 direction already chosen (`analysis-h31-stripe-billing-retirement.md`, lines 42-49 — retire, not migrate). The decision is settled on three independent grounds (canonical plan, reference posture, H31 analysis); do not re-litigate it. What this nudge adds is the full closure set so Stripe Billing is *settled once* and never has to be reopened — the risk in a deprecation drop is not the decision, it is the loose ends. As always: verify every claim below against source before acting; the file:line anchors are starting points, not gospel.

**The decision is settled — three ways.** (a) The canonical plan dropped it: owner-resolved Q6 (2026-06-14) classifies the WCPay-native subscriptions *engine* (Stripe Billing) as **Bucket D — deprecated, do not migrate**, preserving only the gateway↔WC-Subscriptions-extension *integration* (Bucket C). See `implementation-plan.md:209`, `design-spec.md:251`, `bc-manifest.md:15`. (b) The reference is deprecating it itself: an explicit "WooPayments no longer supports this feature" merchant note (`includes/notes/class-wc-payments-notes-stripe-billing-deprecation.php:56-57`) plus a built one-way migrator that cancels the Stripe subscription and hands renewals to tokenized WC Subscriptions (`includes/subscriptions/class-wc-payments-subscriptions-migrator.php:13,175,252`). (c) H31 independently reached the same call. So: **retire it. Do not port the `invoice.*` handlers or any `includes/subscriptions/` engine code into core.**

**Definition of done — Stripe Billing is "settled" only when all of the following hold:**

1. **Inert scaffolding removed.** Native carries deprecated engine *semantics* with no engine behind them: `should_use_stripe_billing()`, the `_wcpay_feature_subscriptions` / `_wcpay_feature_stripe_billing` flag reads, and the `gateway_scheduled_payments` `supports[]` swap (`NativeWooPaymentsGateway.php:77,82,918-923,1038`). Remove them so core never advertises a billing mode it cannot fulfill. (H31's RED tests already assert this end state — finish the GREEN.)

2. **The data-safety guard is the load-bearing piece — make it airtight.** This is where "cleanly" actually lives, because of one failure mode tied directly to §0.6 invariant #5 (no money moves without verification): a merchant with live Stripe-Billing subscriptions has billing schedules running **on Stripe's side**, and Stripe will keep emitting `invoice.upcoming → invoice.paid` on its own clock regardless of core. Today those events *throw* (fail-closed, visible) and block cutover via `provider_events_undispositioned` (`WooPaymentsEventIngestor.php:43-47,~429`; `WooPaymentsCutoverController.php:338`). H31 changes them from *throw* to *removed from `KNOWN_UNHANDLED`* — i.e. from loud-throw to silent-ignore. For any merchant who slips past the guard, a silently-ignored `invoice.paid` means **customer charged on Stripe, no WC renewal order, no fulfillment, no record** — strictly worse than the current throw. So the guard (`WooPaymentsLegacySubscriptionsGuard` + the `legacy_stripe_billing_subscriptions_present` cutover failure) must satisfy:
   - **Ordering:** the guard must block cutover *before* `invoice.*` are de-dispositioned. There must be no window where invoice events can reach native and be dropped. (Pre-cutover the standalone plugin owns the webhook route, so native should never receive them; the guard is what guarantees that stays true.)
   - **Detection completeness:** detect live data across `_wcpay_subscription_id` **and** the migrator's `_migrated_*`-prefixed variants, across all subscription statuses that still bill, not just `active`. A miss here is an off-ledger merchant. Verify the exact meta key set against the reference (`class-wc-payments-subscription-service.php:34-48`, `class-wc-payments-invoice-service.php:26,33`).
   - **Loud, not silent, after removal:** the post-removal behavior for an `invoice.*` event that *does* arrive at native must be a *deliberate, logged* ignore — never a bare fall-through. Its arrival means the guard failed, so it is an alarm, not a no-op. (This also resolves Fermat's earlier webhook-observability finding for this surface.)

3. **The merchant migration path is coherent and signposted.** The migrator lives *in the plugin*, and cutover *deactivates the plugin*, and the migrator hard-requires WC Subscriptions installed (`migrator:175`). So the only safe sequence is: install WC Subscriptions → run the plugin's Stripe Billing migration → *then* cut over. The guard enforces that ordering; its failure message must point merchants there (link/instruct), or the block reads as a dead-end. Confirm there is no core-native expectation that a migrator exists post-cutover — there is none, and there should be none.

4. **Bucket C is provably untouched.** The cut must not nick the preserved integration: tokenized WC-Subscriptions renewals (`scheduled_subscription_payment` on `woocommerce_scheduled_subscription_payment_woocommerce_payments`), change-payment-method, failing-payment-method copy, and the failed-renewal/auth emails (H23) must all still work. Add/keep a regression that drives a tokenized renewal *after* the Stripe Billing removal and proves it still passes — the retire slice and the Bucket-C integration share `NativeWooPaymentsGateway`, so prove they were cleanly separated.

5. **Persisted legacy data is dispositioned, not destroyed.** Bucket D drops the *engine*, not merchants' historical records. Native must **stop writing and stop depending on** `_wcpay_subscription_id`, `_wcpay_subscription_item_id`, `_wcpay_billing_invoice_id`, `_wcpay_pending_invoice_id`, and the product sync meta (`_wcpay_product_id_*`, `_wcpay_product_price_id_*`) — but it must **not actively delete** that merchant data. The guard reads it; nothing else should. Pay special attention to the order-level invoice meta (`_wcpay_billing_invoice_id` / `_wcpay_pending_invoice_id`), which can sit on *orders*, not just subscriptions — the canonical plan under-specified it (see point 6).

6. **Write the disposition back as authoritative.** The canonical docs never bucket `invoice.paid` / `invoice.payment_failed` / `invoice.upcoming` *by name* — their drop is only *inferred* from the general "dropped emitter surface → retire" rule (`bc-manifest.md:100`), and the order-level invoice meta is under-specified. H31 is effectively resolving an ambiguity the plan left open. Record that resolution — the explicit retire-and-guard disposition for the invoice events and the invoice/subscription meta — in `staging-log.md` and the `spec-conformance-baseline.md`, so the gap is *closed*, not locally patched. This is exactly the kind of cross-doc disposition the N5/N6 baseline exists to hold.

**Ask:** complete H31 as a single coherent slice that satisfies all six points above, fail-closed, so the Stripe Billing question is closed for good. Treat the guard (point 2) as the highest-stakes element — it is the one piece that stands between a clean drop and silent off-ledger charges.

**Verify:** (a) source-verify the reference deprecation/migration machinery (`subscriptions-migrator`, `subscriptions-disabler` — note it deliberately keeps invoice webhooks alive while killing the UI, `disabler:34-44` — and the deprecation note) before finalizing the guard's detection set and messaging; (b) TDD through it — finish the existing RED tests, and add guard tests covering live-sub-present-blocks-cutover, migrated-marker-variant-detected, and clean-store-allows-cutover; (c) prove Bucket C with a post-removal tokenized renewal run; (d) run the whole slice through the standing stage gate (N5), since it touches A2/A5 cutover, Workstream C, and Workstream D together. **Boundaries:** do not implement Stripe Billing; do not delete merchant data; do not modify the standalone plugin or the reference checkout; do not weaken the Bucket-C integration; no push.

## N10 — A4 exit gate: prove the dedupe payoff, and write the route-architecture decision into the baseline

> Two A4 *exit-gate* obligations: measure A4's dedupe payoff, and record the route-architecture decision in the audited baseline. These are stage-boundary obligations applied when A4 is declared complete, not per-slice work. Verify every claim against source before acting.

**(a) The A4 exit gate must *measure* the aggregate dedupe / single-registry / bundle delta — not just parity.** "A single `@wordpress/data` registry across *all* of A4" and "total admin bundle smaller than the plugin baseline" are *aggregate* properties that only become checkable at the stage boundary — the same N5-stage-gate logic that motivated this series (good local diffs do not compose into a proven whole). The bundle/runtime reduction *is* the point of native over the plugin, so per §0.6 #4 and the design-spec A4 reduction goal it must be **measured, not assumed** — the N6/N7 "no declaring done on assumption" discipline. The **A4 exit gate (the N5 stage gate for A4)** must, in addition to surface parity, assert (1) a **single `@wordpress/data` registry** — all native admin surfaces use the Core registry, not a parallel one; (2) **no duplicated admin runtime/deps** — WooPayments admin code is bundled by the Core WC Admin pipeline and shares Core's React/components/data, with separate *lazy chunks* preserved (separability is good and intended — not the same as a duplicated runtime); and (3) a recorded **bundle delta** versus the plugin baseline, via the N7c bundle gate. "Renders + matches reference" is necessary but not sufficient for A4 to exit.

**(b) Write the route-architecture decision into the baseline as a first-class design decision.** The decision that native provider admin pages are **provider-neutral sub-routes of Core Settings → Payments** (via a thin Core-owned route registry that future native providers and 3PD extensions register into), with plugin-era top-level `/payments/*` paths demoted to explicit, tested **compatibility aliases**, currently lives only inside `analysis-a4b-admin-dashboard-surface.md`. It is a real refinement of the canonical A4 contract (which named a top-level `/payments/*` route list) and — because this seam is intended to be *the* third-party-provider admin abstraction the public-API track depends on — it is load-bearing enough to be audited, not emergent. Record it in `spec-conformance-baseline.md` (reconciled against the design intent) as the authoritative native A4 route-ownership model, so the A4 exit gate diffs against an explicit target rather than a slice note. Same write-back discipline as N9 point 6 and the N6 baseline rationale.

**Ask:** at A4's boundary, the N5 A4 stage gate must assert (a) the aggregate dedupe / single-registry / bundle-delta measurement so A4 cannot be declared complete on parity alone; and the baseline must carry (b) the route-architecture write-back.

**Verify:** the N7c bundle gate already exists as the harness for the (a) delta — point it at the full set of native WooPayments admin chunks at A4 exit and compare against the plugin baseline. For the single-registry assertion, confirm at exit that no A4 surface (including the settings page) stands up a parallel `@wordpress/data` store outside the Core registry.
