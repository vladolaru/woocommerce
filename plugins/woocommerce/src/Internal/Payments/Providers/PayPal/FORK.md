## Keeping up with the extension

The extension clone is the read-only source. The tooling lives in the plugin's source tree at `bin/paypal-wallet-fork/` (see its `README.md`; `.distignore` excludes `/bin/` and `*.md`, so the tooling, this file and the appendix are in the repository but not in the release zip), and every script finds its sibling files relative to its own location. `bin/paypal-wallet-fork/path-map.json` maps every forked file to its core path, including the extension's root files (main file, `bootstrap.php`, `modules.php`, `webpack.config.js`, `package.json`, `composer.json`), and marks files dropped in core as `null`. Its JS rows point into `client/admin` and `client/blocks`, where the wallet JS lives, so an extension change to a JS file lands on the file named in the report. `bin/paypal-wallet-fork/drift-report.sh <extension clone> <since-ref> [<until-ref>]` (run from `plugins/woocommerce`) lists extension commits since the fork point that touch mapped paths, grouped by core file (dropped files come last under "(dropped in core)"), and marks the ones that touch a shared-contract name, read from `contract-appendix.md` beside this file (regenerate it with `bin/paypal-wallet-fork/contract-list.sh <extension clone>`, which writes the file itself and leaves it untouched if generation fails; at the same extension commit the output is byte-identical, so a regeneration that shows a diff means the extension moved). The audit outputs of the one-shot fork stay in the git-ignored session folder `.agents/scratchpad/sessions/2026-09-30-paypal-wallet-in-core-poc/tools/fork-wallet/`. Port or reject each by hand, then record the new fork point here. There is no automatic merge.

The three stored DTO files are always marked as contract: any upstream change to `modules/ppcp-settings/src/DTO/LocationStylingDTO.php`, `PayLaterMessagingDTO.php` or `OAuthConnectionDTO.php` must be mirrored into `Wallet/SerializedClasses/` in the same release (see below).

## Accepted consequences of the cuts

**Fastlane settings migration.** The settings cut (commit `4b11ba4ce2`) removed `FastlaneSettingsMigration` and `FastlaneSettings`. On a store that still has legacy (3.x UI) settings and where core's wallet is the first copy to run the settings migration, core completes the migration without the Fastlane step and sets the shared `woocommerce_ppcp-settings-migration-is-done` marker. The extension then sees the marker and never migrates the legacy Fastlane settings into `woocommerce-ppcp-data-fastlane`, so its Fastlane configuration starts from defaults. At `e69b0cd003` the vendored copy migrated Fastlane too. This is accepted because Fastlane is outside the wallet; the alternative was to keep both classes. The legacy `axo_enabled` flag is still mapped to the stored Fastlane gateway ID, so a merchant's old choice is not lost.

**Hook object types.** `woocommerce_paypal_payments_built_container` and Modularity's own lifecycle hooks now pass core-namespaced (prefixed) objects, so a third-party callback that type-hints the extension's container or module interfaces will not match core's copy, the same as when the extension is absent. The shell also ignores any module returned by the `woocommerce_paypal_payments_modules` filter that is not core's prefixed `Module` interface, instead of failing at boot.

**Subscriptions created through the extension's card gateways.** Core no longer listens to `woocommerce_scheduled_subscription_payment_ppcp-credit-card-gateway`, so those subscriptions stop renewing while core owns the wallet. Handing the wallet back to the extension resumes them.

**Webhook events of hosted subscriptions.** On a webhook registered earlier, `BILLING.SUBSCRIPTION.CANCELLED` and the three plan events get HTTP 200 and are dropped, so PayPal never retries. A hosted subscription cancelled at PayPal stays active in WooCommerce until the extension takes over again.

**Connect nudges on a dormant store.** The wallet's own connect task (the WooCommerce Home task), its connect admin notice (`ConnectAdminNotice`) and its loading-screen CSS were removed with the connect-surface trims (see "The connect-surface trims (Task 3)" below), so a plain dormant store, with no connection and no collecting state, shows none of them. Its nudge is the "Complete setup" row in the Payments settings list. Core's own surfaces replace the wallet's for the collecting state: the setup task and the Inbox note appear once a first wallet order exists on a store that is not connected, the row notice while the store still collects, and the order-screen and plugins-page notices (see "Seams for the after-payment flow").

**PayPal suggestions in the Payments settings list.** While core holds the native wallet, the list shows no PayPal suggestion: `PaymentsProviders::get_extension_suggestions()` skips both `paypal_wallet` and `paypal_full_stack`. A merchant who wants the full PayPal Payments extension installs it from the Marketplace, and it takes the wallet over. `PaymentsExtensionSuggestionsCountryPlacementTest` pins the extension as owner for its fixtures, which describe the catalog, and checks every country again under core's wallet: the same placement without the two PayPal suggestions.

**Block editor styles under unified editor assets.** The five wallet blocks have their `block.json` under `assets/client/blocks/`, so core's block type controller treats them as bundled WooCommerce blocks. With the experimental, off-by-default unified block editor assets feature on, it replaces the Pay Later Messaging block's editor style (`ppcp-paylater-block-style`) with `wc-block-library-style`, and the block loses its editor styling. Whoever graduates that feature needs to carry the wallet's `edit.css` into it. The block reference generator and the deprecated editor-handle shim are the other two core scanners that see this folder; the generator lists the five wallet blocks in the public block reference (see "The block namespace" under Conventions), and the shim never reaches the wallet's subdirectory (see the JS row above).

## Stored class names (compatibility shim)

The wallet's settings data models save their data as it is, so the options `woocommerce-ppcp-data-styling`, `woocommerce-ppcp-data-paylater-messaging` and (for an hour during OAuth) `ppcp_oauth_connection_details` hold PHP objects, and a serialized object carries its class name. The extension reads and writes the same options, so `LocationStylingDTO`, `PayLaterMessagingDTO` and `OAuthConnectionDTO` keep the extension's names, `WooCommerce\PayPalCommerce\Settings\DTO\*`, byte for byte. They live in `Wallet/SerializedClasses/`, outside any PSR-4 match so Composer's optimized classmap skips them. `load.php` defines them with guards, before the module list is built, and aliases each to its name in the wallet namespace so forked code is unchanged.

This is a shim, not a design to keep: the extension is expected to store arrays and read either shape in a coming release. Once that release is the coexistence floor, core switches to arrays and deletes the directory.

Known residue: the Jetpack autoloader's manifest still lists the three classes (it scans PSR-4 roots as plain classmaps), so with the extension active its loader can serve core's copy. That is harmless only while the files stay identical to the extension's. The session and seller-status caches that hold entity objects are checked with `instanceof` by their readers and rebuild themselves, so they need no shim.

## Conventions

These are deliberate choices that keep the fork's behaviour and shared state as they are. Each one says what would end it.

- **The stored-class shim.** `Wallet/SerializedClasses/` keeps three classes under the extension's names so that objects stored in shared options still load (see "Stored class names" above). They are byte-identical to the extension's by design, so `phpcs.xml` excludes exactly those three files (`LocationStylingDTO.php`, `OAuthConnectionDTO.php` and `PayLaterMessagingDTO.php`) and nothing else under `Wallet/`; `load.php` beside them is linted. When the extension stores arrays, the classes, their phpcs exclusion and the `php-stubs/paypal-wallet-serialized-dtos.php` stub are deleted together.
- **Fired-but-empty group filters.** The card and local payment method groups of the payment methods definition are empty. Their hooks, `woocommerce_paypal_payments_gateway_group_cards` and `woocommerce_paypal_payments_gateway_group_apm`, still fire over an empty array, so third-party callbacks stay valid. The shell adds no settings filters of its own.
- **The block namespace.** The five wallet blocks keep the `woocommerce-paypal-payments/` namespace on purpose, and the block reference lists them under it. Block names are saved in post content, and whoever owns the wallet, core or the extension, registers the same names, so content survives a switch in either direction. Only one side registers them at a time, because the extension wins whenever it is active and core boots the wallet only when it owns the site. Renaming them would orphan every saved block.
- **Block attribute defaults.** The five wallet `block.json` files keep their attribute defaults, byte-identical to the extension's, although root `AGENTS.md` asks new blocks not to declare defaults. They are not new block contracts: posts saved by either copy share one stored format, and the block editor leaves out any attribute equal to its default when it saves. Existing content relies on them: the `lock` default (`remove: true`) of the cart, checkout and product Pay Later blocks and the product buttons block keeps them in place, and the Pay Later Messages defaults (layout, logo, position, color, size, flex color and ratio, placement) fill what saved posts left out. Moving them into edit, save or render code would copy the extension's values into a second place that drifts without notice, and the `lock` default has no such place. Ends when the extension drops its defaults, or when core stops sharing these blocks with it.
- **Dormant mode.** When the store has no connected PayPal account (the connection options of the extension's settings say so), the wallet is not built and none of its hooks, scripts or routes load, except on its own admin pages (the settings route and the old `section=ppcp-gateway` URL) and its REST routes (`/wc/v3/wc_paypal` and `/paypal/v1`), where it boots so a merchant can connect. The Payments settings list shows a placeholder "PayPal Wallet" row (`DormantPayPalGateway`, which shares the wallet gateway's ID and only reads its settings) with a setup button that opens the wallet's settings route. The placeholder never writes an option.
- **The settings route.** The wallet's settings page lives at `admin.php?page=wc-settings&tab=checkout&path=/paypal-wallet`, inside the Payments settings app. The old `section=ppcp-gateway` URL, and the sections of the extension's other gateways, redirect to it with a 302 that keeps the query arguments, so links and the onboarding return keep working.
- **Card funding is off by decision.** Core disables card funding in the PayPal button stack (`DisabledFundingSources` always adds `card`), and no merchant setting is planned. The card button is PayPal-hosted guest card acceptance: the extension's own card button gateway, which the card cut removed together with its 3D Secure and fraud handling. It is not wallet functionality. PayPal's own guest card path inside the PayPal popup is unaffected by `disable-funding=card`, so a shopper without a PayPal account can still pay by card there. Bringing the separate card button back would be a decision about cards, not about the wallet.
- **Core-owned names for the collecting state.** Everything the collecting state adds uses `wc_paypal_wallet`, `woocommerce_paypal_wallet` or `collecting.` (the container's service IDs and extension keys), never `ppcp`, so the extension's names stay the extension's. New hooks carry `@since 11.3.0` and untyped parameters that their callbacks validate. The last section of `contract-appendix.md` lists the names and is generated from the tree. Nothing ends this convention; it keeps the grep for `ppcp` honest.
- **The collecting state is additional to the fork.** Its code lives in `Collecting/` beside `Wallet/`, its tests in `tests/php/src/Internal/Payments/Providers/PayPal/Collecting/` and its JS in `client/admin/client/paypal-wallet/collecting/`. Forked files change only at the seams listed under "Seams for the after-payment flow", one hunk each. The shell (`PayPalWalletBootstrap.php`, `PayPalWalletRuntimeArbiter.php`) is core-owned and may change. Ends with the removal described under "Removing the collecting state".
- **The storefront runs on the v5 SDK path while the platform serves the store.** A store the platform serves is one in the collecting state or the platform-connected state. For such a store `sdk-v6.buttons-available` is false and the buttons use the v5 `SmartButton` path, with the platform app's client ID and the payee as `merchant-id`. The v6 layer has no `merchant-id` and mints its client token from merchant credentials, so it cannot sell for a payee that has no PayPal account (Rulings 66 and 73). The transport interface has no `sdk_client_token()` for that reason; enabling v6 for such stores adds it. No settings-app data carries the v6 flag, so the panel cannot show the limit (Ruling 123). Ends when the v6 layer can take a payee and a platform client ID.

## Seams for the after-payment flow

It is added to the fork, not edited into it. `Collecting/` attaches through the extension's own extension points where one exists: the container's `extensions.php` mechanism, the `woocommerce_paypal_payments_*` and `ppcp_*` hooks the fork fires, and core's task, note, email and admin hooks. ## Deviations, consequences and follow-ups of the collecting state

**A write the fork makes on a served store (Ruling 167).** `Wallet/SavePaymentMethods/SavePaymentMethodsModule.php`, lines 61 to 75: on `woocommerce_paypal_payments_gateway_migrate_on_update` (it fires when `woocommerce-ppcp-version` differs from the plugin's version), a store whose reference transactions are off gets `save_paypal_and_venmo` set to false in the wallet's settings. There is no collecting gate. It is the fork's own behavior and stays.

**BC note for direct refund callers (Ruling 85).** While a refund is locked, `wcgateway.processor.refunds` throws the wallet's `RuntimeException`. `wc_refund_payment()` converts it to a `WP_Error` with the message; `process_refund()` is typed `bool` and cannot return one, so a third-party caller of `process_refund()` directly gets the exception. No core caller does.

**The reconcile is module-bound (Rulings 94 and 178; deviation from spec §5).** A collecting store that disabled the gateway with held orders is reconciled only once the gateway is enabled again. The held-order surfaces stay registered, so the merchant still sees the orders and deadlines. The hand-back case is covered, because a served store boots. The module also has no handler for `MERCHANT.PARTNER-CONSENT.REVOKED`. Both are POC limits: building the fork's completion path without the container was out of scope. Held orders at a first-party connect are stranded until the merchant settles them by hand (R201): see the next paragraph.

**Leaving for a first-party connection (R201, finding I1).** When the shared settings option is saved with first-party credentials, `OwnerIndependent` calls `abandon( 'first_party' )`, which deletes the collecting option, the platform option, the cached seller status and the platform apps' token transients: first-party credentials win over everything. It runs from the add and update hooks of `woocommerce-ppcp-data-common` and, as a fallback, from the `admin_init` callback, whatever the note state, so a later first-party disconnect leaves the store dormant instead of serving the old payee again. The extension saves its connection in the same option, and `OwnerIndependent` runs whoever owns the wallet, so connecting the extension after a takeover is a first-party connect too: it leaves the state the takeover kept for held orders, and the hand-back reconcile then never runs for them (finding m9). Held orders do not keep the state. The held-order surfaces stay registered, because the first-order record keeps the store's wallet history: the held meta keeps the Refund button locked, and each order keeps its on-hold status and its "Payment held by PayPal" note with the deadline. The setup copy goes, as for any connected store: the order notice, the task and the row notice show only while the store collects, and the note is actioned. No reconcile runs (the store boots first-party, without the collecting module), so held orders at a first-party connect are stranded until the merchant settles them by hand.

**One held marker (finding I2).** An order is held while it carries `_wc_paypal_wallet_held_capture`, whatever its status. The held-orders list is that meta on wallet orders, without refunded ones. It includes orders the merchant cancelled by hand, so the reconcile settles them, since PayPal still holds their money and the meta still locks their refunds (finding I-1), and it is ordered by date, then ID. Settlement acts on the meta: a completed capture brings an order on hold or pending payment to paid through the wallet's handler, and a returned one cancels an order on hold with a restock; any other order keeps its status and stock, gets the meta released and a note, and a returned payment still sends the admin email, with wording for that case. `PAYMENT.CAPTURE.REVERSED`, `REFUNDED` and `DENIED` go to the collecting handler whenever the meta is present, so the wallet's `PaymentCaptureRefunded` never creates a WooCommerce refund for money PayPal returned.

**The refund lock is the shell's (finding I4).** `OwnerIndependent` registers the Refund button's lock at priority 1 for any store with wallet history, so it holds whoever owns the wallet and whether the gateway is on. The server-side refusal stays the `LockingRefundProcessor` extension, which exists only while the module boots; under the extension the button is locked and the extension's own refund path runs if called directly.

**The after-consent refund (R202, finding I3).** The one signing path that differs from the pin. While the store is platform connected, `Transport/AssertedRefundSigner` re-signs `POST v2/payments/captures/{id}/refund` on the transport's hosts with the platform app's token and `PayPal-Auth-Assertion` for the connected seller, through the fork's `ppcp_request_args` filter (priority 30) and its retry filter (priority 30). On a retry the module's order-app retry filter (priority 20) leaves a request that carries the assertion alone, so the merchant app's token is not dropped, and the signer re-signs with a fresh platform token; when it cannot, it drops the assertion, so the bearer and the assertion go out together or not at all. A transport that is not configured signs nothing. The order GET that `RefundProcessor` makes first, the capture reads and the refund-fee read stay on the pinned app, which alone can see the order (sandbox run 3, X2 and X3); run 1 is the only evidence that the platform app can refund a merchant-app capture by capture ID once the seller consented, so scenario C's refund step is the test of this path. While collecting no seller is known and nothing is re-signed.

**The reconcile is bounded (finding I6).** A run settles at most 25 held orders, oldest first, and queues an async continuation (`woocommerce_paypal_wallet_reconcile` with the arguments `[ offset, true ]`, group `wc-paypal-wallet`, not unique) when more are held. The offset skips only the orders of the batch that stay held (still pending, or failed to read); a batch that settled nothing and left nothing listed queues nothing, so a chain always ends and the daily run picks up the rest. A continuation does not check the seller status again. The panel's "Check status" reads the seller status first, on its own (`Reconciler::reconcile_onboarding()`), then settles one batch.

**A held capture recorded from its webhook (finding M6).** `Webhook/HeldCapturePending` takes a `PAYMENT.CAPTURE.PENDING` event whose reason is `UNILATERAL` or `PAYEE_SETUP_PENDING` for a wallet order with no held meta, as when the checkout request died after PayPal answered. It fires `woocommerce_paypal_wallet_capture_pending`, so the same bookkeeping runs as at checkout, moves the deadline to PayPal's create time and puts a pending or failed order on hold. An order that already settled (paid, or returned) is left alone, so a late or retried delivery never holds it again. Other pending captures stay with the wallet's handler.

**Smaller edges (findings M1, M3, M4, M5, M8 and M11).** A served store whose transport is not configured reports no merchant email, so the wallet's gateway disabler takes the gateway off the checkout. `wc paypal-wallet collect` without `--sandbox` takes the configured transport's environment, refuses a flag that names the other one, and a bound payee cannot be entered again in another environment. Entering the same unbound payee again keeps its tracking ID, so a referral already opened still matches. The partner referral that the panel's "Complete setup" asks for carries the payee email in the referral's top-level `email` field, so PayPal prefills the sign-up form with it (R209); the transport's debug log line of that request carries the payee email, personal data the log already holds in the order-create bodies, which include the payee. The webhook endpoint refuses a delivery that lacks one of PayPal's five signature headers, or whose certificate URL is not HTTPS on one of PayPal's four API hosts, whose algorithm is not SHA256withRSA or whose transmission time does not parse, before any order lookup or call to PayPal. While the extension owns the wallet, the Payments row notice is not added to the extension's row, the Home task points at the Plugins page, and the order screen uses the Plugins page's wording; the Inbox note keeps the settings link it was created with, since a stored note's action is not rewritten.

**The autoloaded set is the authority for the state (finding I5 and m3).** `ConnectionState` reads the collecting and platform options only when they are in `wp_load_alloptions()`, so a store with neither, or with one, queries nothing for the other. Both are written autoloaded. An option a tool or `wp option set --autoload=off` stored without autoload reads as absent, so the store resolves dormant and stops serving PayPal until the autoload flag is set again; a test pins this.

**The consent check is loose (finding M9).** `DirectPlatformTransport::seller_status()` counts any `oauth_third_party` integration as consent, without checking that it names the platform's partner. A POC limit: the platform service will check the partner.

**The partners-endpoint constructor coupling.** `MerchantlessPartnersEndpoint` extends `PartnersEndpoint` and the `api.endpoint.partners` extension passes the fork's eight constructor arguments through. An extension change to that constructor breaks it at the next port; the drift report marks that file's commits. The fork's retry filter (`ppcp_retry_request_args` at priority 10 in `ApiClient/ApiModule.php`) drops the cached bearer; the module's `BearerRetryFilter` runs at 20 and the transport adds its own at `PHP_INT_MAX` for a single call. That filter is a seam candidate: a hook in the fork that names the app would end the ordering dependence.

**Coexistence: the modules filter (K6, the R26 risk seen live).** The extension's `bootstrap.php` applies `woocommerce_paypal_payments_modules` and hands every module to its own `Package::addModule()`. When the extension is activated in a request where core booted first (WP-CLI, the Payments screen's Install and Enable card through REST, AJAX activation), core's `CollectingModule` reached that call and threw a `TypeError`, a fatal during activation on a store the platform serves. The shell now removes its `append_collecting_module()` callback right after its own `apply_filters()`, and the callback appends only to a list that holds at least one of the fork's `Module` instances, so a later list of the extension's modules comes back unchanged. The activation guard still covers `plugins.php` only; the other activation paths now rely on the filter being gone. The shell's other coexistence behavior is unchanged.

## Lint

The Wallet tree is linted like the rest of core. PHPStan (level 8) analyses it with no entry in `phpstan-baseline.neon`. Three analysis-only stubs in `php-stubs/`, wired through `scanFiles` and never loaded at runtime, stand in for what core's analysis cannot see: `wc-subscriptions.php` (the WooCommerce Subscriptions classes and functions the tree calls, with the signatures of WooCommerce Subscriptions 9.0.1), `paypal-wallet-serialized-dtos.php` (the three aliased DTO names, declared as subclasses of the real classes) and `paypal-wallet-constants.php` (the extension constants that `PayPalWalletBootstrap` defines in a loop). phpcs covers the Wallet source and its tests under the committed `phpcs.xml`; its one exclusion there is the three shim files above. The JS is linted by the admin and blocks clients' own ESLint configs, which carry no wallet demotions, and oxlint reports nothing; the admin app lints with 3 warnings and the blocks wallet code with 44, all of them inherited patterns carried on purpose (`no-require-imports` in tests that reset modules, `exhaustive-deps` effects that need a decision with the UI under test, a few `no-console` debug paths).

Suppression is inline and counted. Plan C added no file-level suppression; its one block pair is a `phpcs:disable` and `phpcs:enable` around the dead body of `WebhookSimulation::start()` (an unconditional `return;` that the extension has had since its 3.3.1 release, followed by the old body, kept so drift porting still applies). Inherited block and file-level disables that the pass did not need to touch stay as the extension has them. At the head of plan C, `Wallet/` holds:

| Marker | Lines | Inherited | Added by plan C |
|--------|------:|-----------|-----------------|
| `phpcs:ignore` | 219 | 63 before plan C, 52 of them unchanged | 167 lines written or rewritten, each with its reason on the line (the `Todo` ones sit on the line above their comment) |
| `phpcs:disable` | 13 | 26 before plan C, 12 kept; 14 removed or replaced by same-line ignores | 1 (the `WebhookSimulation::start()` pair above) |

Every added ignore names the sniff or identifier and says why the code stays as it is (a signature fixed by a hook or a parent, an escaping that would change a value read by code, a failure path the extension has too). A few members the extension never used keep an ignore instead of a deletion, so drift porting stays mechanical: the `SingletonTrait`, `Token::$created` and `PaymentMethodsDefinition::$general_settings`.
